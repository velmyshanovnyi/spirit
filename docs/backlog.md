## 🔴 P0 — критичні

### [ ] A1. PoW блокує головний потік на ~3–5 с при КОЖНОМУ свіжому візиті

**Докази (живий вимір, `spirit.kolo.media`, ця сесія):**
```
solvePow(challenge, 16) → 2952 / 2981 / 5614 / 8325 мс  (медіана ≈ 3 с)
Під час 5.6 с розв'язання: timerSamples = 0
   (жоден setTimeout за 5.6 с не спрацював → потік заблоковано ПОВНІСТЮ)
domContentLoaded = 3550–3787 мс, тоді як увесь JS завантажено за 288 мс
```

**Суть.** Zero-click ефемерний автостарт (H5) одразу викликає `createInvite` →
`solvePow` (SR2, anti-Sybil). `solvePow` крутить `crypto.subtle.digest`
батчами по 256 у циклі `await` — і хоча самі хеші асинхронні, цикл не віддає
керування браузеру. Головний потік мертвий ~3 с: не працюють кліки, не
рендериться нічого, **навіть спінер, доданий цією ж сесією, застигає**.

**Це першопричина того, з чим ми боролися всю сесію.** П'ять раундів фіксів
«блимання при завантаженні» (CSS-приховування → структурна перебудова DOM →
спінер) лікували симптом. Реальна причина — 3 секунди замороженого UI.

**Пропозиція:**
- (а) винести `solvePow` у **Web Worker** — потік вільний, спінер живий, UI клікабельний;
- (б) АБО не робити PoW на критичному шляху першого відкриття: створювати invite
  ліниво, у момент, коли користувач реально хоче поділитися посиланням, а не
  одразу при завантаженні;
- (в) перевірити, чи 16 біт — не завелика ціна за anti-Sybil для цього продукту
  (порівняти з фактичним профілем зловживань — можливо, 12–14 достатньо).

Найбільша цінність — (а)+(б) разом. Обов'язково перевірити живо, а не юніт-тестами
(цей клас проблем jsdom не бачить принципово — вже двічі підтверджено в цій фазі).

### [ ] A2. Регрес, який я вніс: модалка пароля з'являється при звичайному вході

**Файл:** `client/js/app.js:1712` (`onRestricted`), викликається з
`postIdentityRoute()` — `client/js/app.js:825, 4072, 4155, 4188, 4257`.

**Докази.** `postIdentityRoute()` повертає `"room"` або `"profile"` — **обидва в
`ADVANCED_ROUTES`** (`app.js:107`). Тобто після входу в портативний акаунт,
відновлення з recovery, розблокування профілю чи пропуску backup заблокований
користувач отримує **непрошену модалку адмін-пароля**, якої він не викликав.
Раніше в цих сценаріях показувався лише тост.

**Корінь.** `onRestricted` — це хук **рівня рендеру**, а не рівня кліку. Він не
відрізняє «користувач натиснув пункт меню» від «застосунок сам навігував».
Через це той самий хук обслуговує два різні наміри.

**Пропозиція:** позначати саме користувацький клік (прапорець у
nav-item-обробнику `router.js`) і відкривати модалку лише для нього; програмна
навігація лишається на тості, як було. Це ж закриває і A3.

### [ ] A3. Замикання розширеного режиму миттєво знову відкриває модалку пароля

**Файл:** `client/js/app.js:1727` + `app.js:213`.

**Докази (знахідка `/code-review`, відтворено пробним тестом).** Розблокований
користувач на `#/server` тисне «Заблокувати розширений режим» →
`onVisibilityChange` диспатчить синтетичний `hashchange` → роутер перерендерює
вже-обмежений поточний маршрут → `onRestricted` спрацьовує з
`!isAdvancedModeUnlocked() === true` → **модалка пароля відкривається одразу
після навмисного замикання**. Ба більше: `pendingRestrictedRoute` записується під
час *замикання*, тож введення пароля поверне користувача на `#/server` — тобто
**замикання саме себе скасовує**.

Наявний тест (`app.test.js:1870`) проходить цей флоу, але перевіряє лише
видимість екрана, тому лишається зеленим.

**Пропозиція:** та сама, що й A2 — розрізняти user-intent; плюс не записувати
`pendingRestrictedRoute` під час події замикання.

## 🟠 P1 — важливі

### [ ] D1. Усі основні контроли менші за мінімальний тач-таргет

**Докази (живий вимір `getBoundingClientRect`):**
```
btn-start-call      42×33      btn-toggle-camera  43×33
btn-toggle-mic      43×33      theme-toggle       36×33
btn-settings-toggle 42×40      lang-select        26×42
btn-send           104×43      message-input       26×43
```
Жоден не досягає 44×44 (WCAG 2.5.5 / Apple HIG 44pt / Material 48dp).
У CSS: `min-height: 44px` — **0 входжень**.

**Чому це важливо саме тут.** Це кнопки дзвінка/камери/мікрофона й шестерня —
основні контроли в шапці. На телефоні (а це заявлений сценарій — кросплатформність
в інваріантах проєкту) промахи по 33-піксельній висоті регулярні.

**Пропозиція:** ввести `--control-min: 44px` і застосувати до `.btn-icon`,
`button`, `select`, `input` через `min-height`/`min-width`; візуально розмір
можна лишити компактним, збільшивши лише клікабельну область (`padding` або
псевдоелемент-хітбокс).

### [ ] A4. `app.js` — God object на 4921 рядок

**Докази.** `client/js/app.js` — 4921 рядок, 51 статичний імпорт, 237 KB.
Секція G1 винесла 5 UI-модулів (5499→4551), але з того часу файл **знову виріс**

### [ ] A5. Нуль лінивого завантаження: 1.2 МБ і 71 запит на старті

**Докази (живий вимір):**
```
71 файл · 1227 KB розпаковано · 335 KB передано · DCL 3.5–3.8 с
Найбільші: i18n.js 321KB · hash-wasm 265KB · app.js 237KB · qrcode 58KB · bip39 23KB
Динамічних import() у client/js: 0
```

Кожен відвідувач качає **всі 11 мов** (з них потрібна одна), **QR-бібліотеку**
(потрібна лише для device-linking), **BIP39-словник** (лише для mnemonic-флоу),
**hash-wasm** (лише для Argon2 детермінованих акаунтів).

**Нюанс, який рятує ситуацію.** Мережа НЕ вузьке місце: увесь JS вантажиться за
288 мс завдяки HTTP/2-мультиплексуванню, парсинг кожного модуля 8–24 мс.
Тому це **P1, а не P0** — реальний біль зараз у A1 (PoW), а не в вазі.

**Пропозиція (після A1):** `await import()` для qrcode / bip39 / hash-wasm за
місцем першого використання; i18n — розбити на файл-на-локаль із динамічним
підвантаженням обраної. Інваріант «без бандлера» це **не порушує** — динамічний
`import()` нативний для ES-модулів.

### [ ] A6. Ratchet: повідомлення тихо зникають при розсинхроні

**Файл:** `client/js/app.js:3520`
```js
if (isRatcheted && !state.receiveChainKey) return; // тихий drop
```
і поруч — `if (!state.sessionKey) return;`.

**Суть.** KDF-ланцюг без обробки пропущених ключів: якщо повідомлення не
розшифрувалося або прийшло поза чергою, ланцюг далі розсинхронізований
**назавжди в межах сесії**, а користувач не отримує жодного сигналу — просто
не бачить повідомлень. DataChannel за замовчуванням ordered+reliable, що
знижує ймовірність, але не прибирає (гілка вище тихо ковтає й той випадок,
коли ключ ще не виведено).

**Пропозиція:** мінімум — не мовчати: показати користувачеві стан «повідомлення
не розшифровано» замість тиші. Максимум — тримати невелике вікно skipped-message
keys (як у Double Ratchet) для стійкості до перестановок.

тести не бачать.

**Пропозиція:** тестова фікстура має відображати реальний `index.html`;
для фічі розблокування — тест, що клікає справжній `.nav-item[data-route]`
у заблокованому стані. Довгостроково — розглянути генерацію фікстури з
реального `index.html`, щоб вони не розходились мовчки.

### [ ] A9. Немає CI: єдиний гейт — дисципліна людини

**Докази.** Деплой — ручний FTP-скрипт; немає GitHub Actions / жодного
автоматичного прогону тестів на push. Проєкт спирається на pre-commit hook і

**Пропозиція:** мінімальний GitHub Actions workflow: `npm ci && npx vitest run`
на кожен push у `main`. Дешево, закриває цілий клас ризиків координації.

## Методологічна нотатка

Три з чотирьох P0/P1-знахідок про поведінку (A1, A2, A3) **не видно юніт-тестам
у jsdom** — вони знайдені живим виміром у браузері й пробними тестами.
Це вже третє підтвердження правила, записаного у Фазі 5: jsdom не бачить
ні реальної продуктивності Web Crypto, ні CSS-каскаду, ні того, що відрізняє
користувацький клік від програмної навігації. Жива перевірка після кожного
деплою лишається обов'язковою.
