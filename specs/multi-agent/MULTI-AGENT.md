# MULTI-AGENT.md — протокол спільної інженерної роботи агентів у одному репозиторії

> **Версія:** 6.0
> **Статус:** нормативний. Цей файл є джерелом істини для поведінки агента, а не порадою.
> **Мова:** пояснення — українською; ідентифікатори, стани, поля, команди — англійською.
> **Спадкоємність:** заміщує `MULTI-AGENT.v2-draft/v3/v3-next/v4/v5`. Розділ 14 пояснює,
> що саме взято, що відкинуто і чому. Старі файли зберігаються як історія рішень.
> **Область:** один Git-репозиторій, кілька незалежних агентів (різні акаунти, різні сесії,
> без спільної пам'яті), плюс люди й CI. Проєктно-незалежний: жодних назв проєктів,
> доменів, шляхів. Приклади — `foo`, `bar`, `example.com`, `TASK-001`, `agent-foo`.
> **Верифікація:** 10 ітерацій незалежного рев'ю з чистим контекстом, кожна — з дослівним
> виконанням bash-рецептів у bare-репозиторії (60 знахідок, усі закрито; iter10 —
> PASS_WITH_NOTES). Артефакти — `specs/reviews/multi-agent-protocol-v6-iter*.md`. Усі
> позначки «(перевірено)» в тексті посилаються на ці прогони. Не перевірялось: поведінка
> хостингів (pre-receive, branch protection) і не-GNU awk/sed/diff.

## 0. Як цим користуватися за 60 секунд

Ти агент, який щойно підключився до репозиторію. Виконай це, нічого не пропускаючи:

```bash
git fetch origin --prune '+refs/heads/*:refs/remotes/origin/*'   # ПОВНИЙ refspec явно: refspec у команді ЗАМІНЮЄ config
                                                                  # (лише task/* → origin/main застаріє), а --single-branch
                                                                  # клон task/* сам не приносить (обидва перевірено)
git log origin/main --oneline -15            # що змінилося без тебе
MAIN=$(git rev-parse --git-common-dir)/..     # ОСНОВНИЙ клон: усередині linked worktree `switch main`
                                              # або падає (main зайнятий), або зносить worktree з task-гілки (перевірено)
git -C "$MAIN" switch -q main && git -C "$MAIN" merge -q --ff-only origin/main \
  && [ "$(git -C "$MAIN" rev-parse HEAD)" = "$(git rev-parse origin/main)" ] \
  || { echo "локальний main ≠ origin/main — у нього хтось комітив локально: СТОП (розділ 9)"; exit 1; }
                                              # fetch НЕ оновлює робоче дерево: без цього кроку все нижче
                                              # читається зі старого checkout'у (перевірено); claim (5.2)
                                              # main не чіпає, тому ff завжди можливий. Рівність SHA —
                                              # окремо: якщо main ЛИШЕ попереду, ff «успішний» (перевірено)
cat MULTI-AGENT.md                            # цей файл
cat PROJECT-BINDING.md                        # прив'язка до проєкту: шляхи, команди, ролі (розділ 12)
git ls-remote origin 'refs/heads/task/*' 'refs/heads/small/*'   # заявки і дрібні зміни — на сервері (5.3, 6.0)
for b in $(git for-each-ref --format='%(refname:short)' refs/remotes/origin/task/); do
  echo "== $b"; git show "$b:specs/handoffs/${b#origin/task/}.md"; done   # стан одиниць У РОБОТІ (5.3)
git for-each-ref --format='%(refname:short)' refs/remotes/origin/small/    # чекають G7-lite від master (6.0)
ls specs/reviews/ | tail -20                  # ухвалені рішення і halt-артефакти — не піднімай їх знову
grep -rn '\- \[ \]' specs/ --exclude-dir=handoffs | head -40   # незавершені одиниці (чекбокси бувають з відступом;
                                                                 # handoffs/ містять заморожені копії з [ ] — не робота)
```

Шляхи `specs/…` і назва гілки `main` у цьому файлі — значення за замовчуванням;
реальні — з `PROJECT-BINDING.md`. Свою роль визнач за правилом 2.0; якщо жодне
джерело не називає тебе master — ти worker.

Далі: обери **одну** одиницю роботи → заяви право на неї (розділ 5) → пройди ворота
G0–G9 (розділ 6) → залиш handoff (розділ 10). Не бери другу, поки перша не закрита
або явно не передана.

Якщо будь-що з розділу 9 («умови СТОП») справджується — зупинись і напиши, що саме,
замість того щоб продовжувати.

## 1. Що це — і чого це НЕ є

### 1.1. Що це

Протокол відповідає на п'ять питань, і тільки на них:

```text
1. Хто зараз має право змінювати цю частину системи?     → ownership
2. Звідки агент знає, що його уявлення про стан свіже?   → freshness
3. Що вважається доказом, що робота зроблена правильно?  → evidence
4. Хто і на підставі чого дозволяє інтеграцію?           → review / integration
5. Що робити, коли стан невідомий?                       → stop / reconcile
```

### 1.2. Чого це НЕ є

Це **не** специфікація розподіленої системи з консенсусом. Попередні версії (особливо v5)
дрейфували саме туди: canonical state store, authentication service, capability tokens,
CAS-примітиви, event log з проєкціями, підписані транзакції. Усе це коректно як теорія —
і неможливо виконати агентові, який має лише git-клон і право пушу на віддалений репозиторій.

Це є ключова помилка, яку v6 виправляє:

```text
Протокол, який неможливо виконати, гірший за відсутність протоколу:
агент читає його, не може дотриматися, відкочується до імпровізації —
і при цьому вважає себе таким, що дотримався.
```

Тому v6 має **обов'язкове ядро, що працює з одним лише git**, і чесно позначені
надбудови (розділ 4).

### 1.3. Головна поправка до моделі загроз

v3-next → v5 будували захист від *конкурентного* агента: split-brain, крадіжка claim,
stale callback, fence token. Це реальні проблеми, але їхня ціна помилки — **rebase**.

Реальна ж модель загроз у роботі агентів на базі мовних моделей інша:

```text
Небезпечний агент — не зловмисний і не той, що гоняється за claim.
Небезпечний агент — це той, що впевнено повідомляє результат, якого не існує.
```

Типові прояви, кожен з яких спостерігався на практиці:

| Що агент повідомив | Що було насправді |
|---|---|
| «виміряв прискорення у 2.4×» | вимір знято зі старого закешованого коду; число випадкове |
| «CSS-селектор виправлено» | селектор структурно не збігався ні з чим у реальному DOM |
| «тест підтверджує поведінку» | тест чекав на неправильну умову й проходив завжди |
| «причина — кешування у service worker» | у файлі не було жодного обробника `fetch` |
| «секцію завершено» | чекбокси проставлені до написання коду |

Проти цього fence token безсилий. Тому центр ваги v6 — **розділ 7 (дисципліна доказів)**,
а координація зведена до мінімуму, який реально перевірено (розділ 5).

## 2. Ролі

Один протокол, два рівні повноважень. Роль **не дає** послаблення у якості.

```text
ROLE=master
ROLE=worker
```

### 2.0. Як агент дізнається свою роль

У порядку пріоритету:

```text
1. roles.master у PROJECT-BINDING.md — перелік ідентифікаторів агентів/акаунтів
2. явна вказівка людини в поточній сесії («працюй як master»)
3. інакше — worker
```

**Ідентифікатор агента (`AGENT_ID`)** — стабільний рядок, який людина призначає
кожному агентові/акаунту (`agent-foo`) і який агент виставляє в `git config user.name`
свого клона. Ним підписуються `OWNER=`, `reviewer:` і рядок `Agent:` у claim-коміті.
Звідки агент його бере — `agent_id.source` у binding (типово `git config user.name`).
Унікальність — відповідальність людини, що веде `roles`. Агент, який не може
визначити свій `AGENT_ID`, не заявляє роботу: умова СТОП.

Агент **не може призначити себе master**. Відсутність будь-кого з роллю master —
не привід для самопризначення, а умова СТОП (розділ 9): роботи у стані `REVIEW`
чекають, поки людина не назве master у binding або в сесії.

**Ієрархія авторитету** (успадкована з v4-RedTeam §6):

```text
обмеження безпеки з PROJECT-BINDING.md
  (protected_paths, secrets.never_commit, escalate_to_human)
        >  master  >  worker
```

Master не може «дозволити» те, що binding забороняє. Це може лише людина, змінивши
binding явним комітом.

> **Про назву.** У попередніх версіях друга роль називалася `slave`. Позначення
> `ROLE=slave` приймається як застарілий синонім `ROLE=worker`, щоб старі документи
> й скрипти не ламалися. У новому тексті вживай `worker`.

### 2.1. MASTER

Може виконувати переходи, недоступні worker:

```text
інтегрувати завершену роботу в захищену гілку
закривати review і фіксувати рішення
змінювати архітектурні специфікації та цей протокол
авторизувати deployment
розблоковувати аварійні стани
скасовувати або переприсвоювати чужу заявку (лише за правилами 5.4)
```

Чого master **не** отримує:

```text
authority != звільнення від тестів
authority != звільнення від review
authority != право оголосити результат без доказів
```

Master не інтегрує **власну** зміну взагалі: G7 для неї виконує інший master або
людина (8.2). Master, який зливає власну зміну сам, порушує протокол так само,
як worker, що робить force-push у `main`.

### 2.2. WORKER

```text
заявити право на вільну одиницю роботи
створити ізольований worktree/гілку
написати тести й реалізацію
виконати перевірку і зафіксувати докази
підготувати review-артефакт
запушити свою task-гілку
передати роботу в стан REVIEW і зупинитися
відрев'юїти ЧУЖУ одиницю і записати артефакт із decision (без закриття review)
```

Чого worker не робить — без винятків (дозвіл людини реалізується зміною `roles`
у binding явним комітом, а не фразою в чаті):

```text
force-push у будь-яку спільну гілку
merge чужої роботи
deploy у production
зміна чужої активної заявки
відключення hooks/CI
зміна нормативного тексту в protected_paths (чекбокси й handoff-записи ВЛАСНОЇ одиниці
    в спеці — частина G9, дозволені)
```

### 2.3. Асиметрія — тільки в переходах

Різниця ролей визначається **виключно** таблицею дозволених переходів (розділ 6.10;
єдиний явний виняток — скорочений шлях 6.0), а не різними стандартами якості. Це успадковано з v2 §1.3 і залишається вірним.

## 3. Аксіоми

```text
A1. Репозиторій — єдиний канал координації.
    Чат, пам'ять моделі та усні домовленості не існують для іншого агента.

A2. Невідомий стан ≠ безпечний стан.
    UNKNOWN не можна відображати в SUCCESS.

A3. Твердження без доказу — не результат, а гіпотеза.

A4. Свіжість не успадковується.
    Те, що ти прочитав стан 20 хвилин тому, не означає, що він досі такий.

A5. Кожна дія має залишати слід, з якого наступний агент відновить картину
    без реверс-інжинірингу.

A6. Обсяг церемонії пропорційний радіусу ураження, а не бажанню бути ретельним.

A7. Безпека важливіша за прогрес. Коли є сумнів — SAFE STOP.
```

Аксіома A6 — нова щодо v2–v5 і принципова. Жодна з попередніх версій не моделювала
**вартість** воріт. Протокол, який вимагає contract hash і двох незалежних рев'юерів
для виправлення одного рядка, буде обійдений цілком, а не деградує плавно.

## 4. Рівні відповідності

Кожен рівень чесно каже, що він реально забезпечує.

### L0 — тільки git (обов'язковий мінімум)

Доступно завжди: клон, `origin`, право пушу.

```text
Забезпечує:  одна одиниця роботи = одна гілка; конкурентний claim через створення ref;
             виявлення застарілої бази; docs/evidence як durable-артефакти.
НЕ забезпечує: неможливість force-push; автентифікацію агента; примусовий review.
Тримається на: дисципліні агента + аудиті постфактум (git-історія все фіксує).
```

**Ядро протоколу (розділи 5–10) виконуване повністю на L0.** Це головна вимога до v6.

### L1 — git + платформні захисти

```text
Додає: protected branch, required status checks, required review, заборона force-push,
       secret scanning, CI.
Закриває: крадіжку claim через force, неперевірену інтеграцію, частину секретів.
Але:   PROTECTED != IMMUTABLE. Захист гілки може обійти адміністратор сервера;
       він дає видимість порушення, а не його неможливість (v4-RedTeam §21, v5 §145).
```

### L2 — L1 + зовнішній координатор стану

```text
Додає: canonical state з версією, CAS/умовні переходи, operation_id як ключ ідемпотентності,
       fence/incarnation з реальною точкою примусу.
Потрібно, коли: агентів багато, вони працюють без людського нагляду, а ціна
       подвійного володіння вища за вартість інфраструктури.
```

### L3 — L2 + атестація

```text
Додає: автентифіковану ідентичність агента, підписані переходи, незмінний аудит,
       attested evidence (результат від довіреного виконавця, а не самозвіт),
       контрольований deployment.
```

**Правило чесності:** реалізація зобов'язана вказати свій рівень у `PROJECT-BINDING.md`
і **не описувати гарантії вищого рівня як наявні**. Запис `fence_token` у YAML на L0 —
не захист, а джерело хибної впевненості: рев'юер побачить поле й припустить, що воно
кимось перевіряється.

## 5. Координація

### 5.1. Одиниця роботи

```text
Одиниця роботи (UNIT) — найменша зміна, яку можна завершити повним циклом
G0–G9 і яка залишає репозиторій у консистентному стані.
```

Секція специфікації, один пункт беклогу, одне виправлення. Не «вся спека».
Якщо одиницю неможливо закрити в межах сесії — її треба **розбити**, а не залишити
напіввідкритою.

Кожна одиниця має стабільний ID: `TASK-001`, `SEC-021`, `A11`. ID не змінюється ніколи.

### 5.2. Claim — перевірена примітива

Заявка на роботу — це **створення на сервері нової гілки `task/<ID>`, вершина якої —
унікальний claim-коміт із handoff-файлом**. Виграє той, чий push дійшов перший;
локальний час і локальний коміт значення не мають.

```bash
set -e                                                  # збій будь-якої КОМАНДИ нижче — claim НЕ робиться
: "${AGENT_ID:?AGENT_ID не задано — СТОП (2.0)}"        # без цього порожній OWNER= пушиться з exit 0 (перевірено)
git fetch origin --prune
git ls-remote origin 'refs/heads/task/*'               # вже заявлене — не чіпай
# перечитай стан одиниці роботи ПІСЛЯ fetch, а не до
! git show-ref --verify --quiet refs/heads/task/TASK-001 \
  || { echo "локальна task/TASK-001 вже існує — спершу 5.5"; exit 1; }

[ ! -e ../wt-TASK-001 ] || { echo "тека ../wt-TASK-001 вже існує — сусідній клон іншого агента? СТОП, чуже не видаляй"; exit 1; }
git worktree add --detach ../wt-TASK-001 origin/main    # від origin/main, локальний main не чіпаємо
cd ../wt-TASK-001
git switch -c task/TASK-001

mkdir -p specs/handoffs                                 # теки може ще не бути (перший claim у проєкті)
CRIT=$(awk -v h='## TASK-001' 'BEGIN{L=index(h," ")-1} {sub(/\r$/,"")} $0==h{f=1;b=0} f&&match($0,/^`+/)&&RLENGTH>=3{if(!b)b=RLENGTH;else if(RLENGTH>=b)b=0} f&&!b&&$0!=h&&match($0,/^#+ /)&&RLENGTH-1<=L{exit} f' specs/foo.md)
[ -n "$CRIT" ] || { echo "секцію '## TASK-001' не знайдено: заголовок має бути ТОЧНО таким — без назви після ID"; exit 1; }
                                                        # ОКРЕМИМ рядком: збій підстановки всередині heredoc
                                                        # set -e не ловить (перевірено)
cat > specs/handoffs/TASK-001.md <<EOF
UNIT=TASK-001
STATE=CLAIMED
OWNER=$AGENT_ID
BASE_SHA=$(git rev-parse HEAD)
CRITERIA_SOURCE=specs/foo.md#TASK-001
CLAIMED_AT=$(date -u +%FT%TZ)
---
$CRIT
EOF
# Після "---" — ДОСЛІВНА копія секції критеріїв приймання на момент claim: handoff і є
# замороженими критеріями. Формат заголовка секції — units_of_work.criteria_section у binding;
# awk бере рівень заголовка з h (L=2 для "## ", 3 для "### "): секція закінчується на наступному
# заголовку ТОГО Ж АБО ВИЩОГО рівня (## після ### теж закриває), глибші (####) — частина секції
# (перевірено: остання ###-секція групи не захоплює наступну "## Групу"). Рядки всередині
# fenced-блоків заголовками НЕ вважаються: інакше "# коментар" у прикладі коду обрізає
# копію мовчки (перевірено). Fence відстежується ВІД ЗАГОЛОВКА СЕКЦІЇ (b=0 при $0==h) і за
# довжиною: ```` закривається лише ```` або довшим, тож 4-backtick обгортка навколо ```
# прикладу не інвертує стан (перевірено). sub(\r$) — CRLF під POSIX awk.
# Заголовок секції має бути ТОЧНО "## <ID>" ($0==h): "## TASK-001 — Назва" не збіжиться.
# Решта полів §10 додаються при переходах — ПЕРЕД "---", ніколи після.

git add specs/handoffs/TASK-001.md
git commit -m "claim TASK-001

Task: TASK-001
Agent: $AGENT_ID"
[ "$(git rev-parse HEAD)" != "$(git rev-parse origin/main)" ]   # claim-коміт справді існує
git push origin task/TASK-001
```

`exit 0` на push → заявку отримано, worktree готовий до роботи. Рецепт зупинився **на
push** → **CLAIM_LOST** (це результат push, не стан одиниці). Рецепт зупинився
**раніше** (немає `AGENT_ID`, не знайдено секцію критеріїв, збій `worktree add`) → claim
не відбувся, на сервері нічого немає, але worktree і локальна гілка вже можуть існувати
(перевірено). В обох випадках — та сама очистка, перш ніж робити будь-що інше:

```bash
cd "$(git rev-parse --git-common-dir)/.."   # основний клон: зсередини worktree його не видалити (перевірено),
                                             # а $REPO тут уже не існує — це нова оболонка після set -e
git worktree remove --force ../wt-TASK-001
git branch -D task/TASK-001                  # інакше наступний claim візьме стару гілку (5.5)
```

Після CLAIM_LOST — перечитай `ls-remote` і handoff переможця (5.3). Якщо `OWNER=` там —
**ти сам** (нова сесія у свіжому клоні на власній одиниці), це не програна гонка, а
повторний вхід: іди в 5.5, не «обирай інше». Інакше — обери інше. Після раннього збою —
усунь причину і повтори рецепт з початку.

`set -e` і перевірка перед push — не педантизм: без них збій `mkdir`/`commit` доходить
до push, порожня гілка на SHA `origin/main` пушиться з `exit 0`, другий агент отримує
`Everything up-to-date` і теж `exit 0` — обидва вважають claim своїм (перевірено).

Кожен елемент рецепта закриває перевірену проблему:

```text
claim-коміт містить OWNER і CLAIMED_AT
    → у двох агентів різні SHA, другий push на ту саму нову гілку ВІДХИЛЯЄТЬСЯ.
      Порожня гілка на тому ж SHA, що й main, НЕ арбітрує: другий push дає
      "Everything up-to-date", exit 0, і обидва вважають claim успішним (перевірено).

worktree від origin/main у detached-стані
    → локальний main не отримує зайвих комітів і не розходиться з origin/main
      мовчки. Claim-коміт на локальному main лишає його "ahead 1" назавжди, а
      `git pull --ff-only` каже "Already up to date" і не попереджає (перевірено).

гілка в refs/heads/*
    → працює на будь-якому сервері з правом пушу. Окремі простори імен
      (refs/coordination/*) деякі хостинги забороняють, а звичайний git fetch їх
      не приносить — claim там невидимий без ls-remote.

CRITERIA_SOURCE + дослівна копія секції після "---"
    → критерії приймання заморожені на момент claim у самому handoff, тож master
      у G7 перевіряє їх без автора. Blob цілого файлу спеки для цього НЕ годиться:
      G9 сусідньої одиниці ставить чекбокс у тому самому файлі, blob змінюється
      для всіх, і всі інші одиниці цієї спеки блокуються (перевірено). Тому G7
      порівнює ТЕКСТ секції на origin/main із копією в handoff після нормалізації
      чекбоксів (`[x]` → `[ ]`); розбіжність — BLOCKED, а не мовчазне продовження.
```

> **Перевірено експериментально** (два клони одного bare-репозиторію, одночасне
> створення `task/TASK-001` з різними claim-комітами): переможець отримує
> `[new branch]` і `exit 0`, той, хто програв, — `! [rejected]` і `exit 1`; локальний
> `main` обох клонів дорівнює `origin/main`. Рівно один виграє. Те саме справджується
> для довільного ref (`refs/coordination/claims/*`) — примітива одна: створення ref.

**Чесне обмеження, теж перевірене:** той, хто програв, може перезаписати гілку
через `git push --force` — команда завершується `exit 0`, і сервер починає
вказувати на його коміт. Тобто:

```text
claim захищає від ЧЕСНОЇ гонки, а не від force-push.
Захист від force існує лише на L1+ (branch protection на сервері).
На L0 claim тримається на дисципліні; git-історія робить порушення видимим постфактум.
```

Це саме та відмінність, яку v4 §9.3 правильно назвала (`PROTOCOL RECORD` vs
`ENFORCEMENT POINT`), але жодна версія не показала на доказі.

### 5.3. Читання заявок

Claim живе на сервері. `git fetch` приносить `task/*` як `origin/task/*` лише за
стандартного refspec і лише станом на момент fetch. Тому перед claim'ом і у воротах G0
виконується саме `git ls-remote origin 'refs/heads/task/*'` — запит до сервера, а не до
локальної копії.

**Handoff і halt-артефакт одиниці в роботі живуть у вершині її task-гілки, а не в гілці
інтеграції** — туди вони потрапляють лише разом з інтеграцією в G7. Тому
`ls specs/handoffs/` на `main` показує виключно вже завершені одиниці (перевірено), і
стан того, що в роботі, читається з гілки:

```bash
git fetch origin --prune '+refs/heads/*:refs/remotes/origin/*'
git show origin/task/TASK-001:specs/handoffs/TASK-001.md
git show origin/task/TASK-001:specs/reviews/TASK-001.halt.md    # якщо STATE=BLOCKED вказує на halt
```

Цикл у розділі 0 / G0 робить це для всіх `origin/task/*` одразу.

Заявка існує з моменту успішного push і ні секундою раніше. Локальне редагування
беклогу чи handoff-файлу заявкою не є (v2 §43 — правило лишається вірним і сьогодні).

### 5.4. Застаріла заявка

Заявка не стає недійсною просто від віку. Переприсвоєння дозволене, лише коли
одночасно виконується все:

```text
минув TTL, заданий у PROJECT-BINDING.md (типово 24h)
І немає нових комітів у task-гілці за цей період
І немає відкритого review
І одиниця не в стані BLOCKED із задокументованою причиною
І handoff у вершині origin/task/<ID> має STATE ∈ {CLAIMED, ACTIVE}
    (REVIEW/APPROVED/INTEGRATED/DONE — це не покинута робота; task-гілки після G7 не видаляються)
І у вершині origin/task/<ID> немає specs/reviews/<ID>.halt.md (7.4; читати з гілки, 5.3)
```

Переприсвоєння виконує **master** і записує явним комітом, який оновлює
`specs/handoffs/<ID>.md` (`OWNER`, `STATE=CLAIMED`, попередній власник у `NOTE` — усі
три **перед** рядком `---`, §10):

```text
RECLAIM TASK-001 <UTC> by agent-bar
Previous: agent-foo, last activity <UTC>, branch task/TASK-001 preserved
Reason: lease expired, no activity
```

Гілку попереднього власника **не видаляти**. Робота могла бути цінною.

### 5.5. Ізоляція

Worktree створюється на кроці claim'у (5.2) від `origin/main` — **ніколи** від
локального `main`. Щоб продовжити вже заявлену гілку в новій сесії:

```bash
set -e
: "${AGENT_ID:?AGENT_ID не задано — СТОП (2.0)}"
git fetch origin --prune '+refs/heads/*:refs/remotes/origin/*'
git worktree prune                             # тека worktree видалена вручну/tmp-cleaner'ом → інакше $WT нижче
                                               # вкаже на неіснуючий шлях і cd впаде (перевірено)
git show-ref --verify --quiet refs/remotes/origin/task/TASK-001 \
  || { echo "на сервері немає task/TASK-001 — claim не відбувся: очисти (5.2) і повтори"; exit 1; }
if git show-ref --verify --quiet refs/heads/task/TASK-001; then
  # локальна гілка вже є: worktree add візьме ЇЇ, а не origin/task/TASK-001 (перевірено)
  git merge-base --is-ancestor task/TASK-001 origin/task/TASK-001 \
    || { echo "локальна task/TASK-001 розійшлася з origin — СТОП (розділ 9)"; exit 1; }
fi
# worktree з 5.2 зазвичай ще існує — знайди його, а не створюй другий
WT=$(git worktree list --porcelain | awk '/^worktree /{p=substr($0,10)} /^branch refs\/heads\/task\/TASK-001$/{print p}')
#                                                  substr, не $2: шлях із пробілом $2 обрізає (перевірено)
if [ -z "$WT" ]; then
  [ ! -e ../wt-TASK-001 ] || { echo "тека ../wt-TASK-001 зайнята чимось іншим — СТОП (розділ 9)"; exit 1; }
  if git show-ref --verify --quiet refs/heads/task/TASK-001; then
    git worktree add ../wt-TASK-001 task/TASK-001                          # локальна гілка вже є
  else
    git worktree add -b task/TASK-001 ../wt-TASK-001 origin/task/TASK-001  # ЯВНО, не DWIM: у --single-branch
                                                                           #   клоні DWIM дає exit 128 (перевірено)
  fi
  # upstream НЕ налаштовуємо: у --single-branch клоні --set-upstream-to на origin/task/* теж
  # падає (перевірено). Протоколу він не потрібен — усі push/fetch тут явні за іменем.
  WT=../wt-TASK-001
fi
cd "$WT"
git merge --ff-only origin/task/TASK-001
OWN=$(sed -n 's/^OWNER=//p' specs/handoffs/TASK-001.md | tr -d '\r')   # tr: CRLF-checkout під POSIX sed
[ "$OWN" = "$AGENT_ID" ] || { echo "OWNER=$OWN, а ти $AGENT_ID — одиницю переприсвоєно (5.4), СТОП"; exit 1; }
```

Без `set -e` і пошуку наявного worktree блок «успішно» завершується при збої
`worktree add` на чужій теці, гілка при цьому вже створена, а агент лишається
в checkout'і `main` (перевірено).

Розходження локальної та серверної гілки — не привід для `--force`: це чужий claim, що
переміг (5.2). RECLAIM (5.4) розходження **не створює** — це звичайний коміт у ту саму
гілку, він fast-forward'иться мовчки; тому власника перевіряє саме рядок `OWNER=`
(перевірено). Обидва випадки — умова СТОП.

Два агенти ніколи не працюють в одному робочому каталозі. Шлях `../wt-<ID>` відносний
до клона, тому клони різних агентів на одній машині тримають у **різних батьківських
теках** — інакше другий агент упреться в чужу теку на кроці claim'у (перевірено; він
зупиниться, а не видалить її, але й claim не зробить).

**Важлива поправка** (її не було до v4-RedTeam §19): ізоляція worktree ≠ повна
ізоляція конфігурації репозиторію — частина `config` спільна між worktree.
І тим більше вона не ізолює те, що лежить поза git:

```text
/tmp, порти, кеші, БД, черги, фонові процеси, глобальні демони
```

Якщо одиниця роботи використовує жорстко зашитий порт чи спільний каталог —
це дефект ізоляції, а не дрібниця. Стан: `BLOCKED` до усунення.

### 5.6. Свіжість бази

```bash
git fetch origin --prune
git merge-base --is-ancestor origin/main HEAD && echo FRESH || echo STALE
git rebase origin/main                                  # якщо STALE
```

Перевірено, і це важливіше, ніж здається: git відхиляє push **лише** туди, де ref
просунув хтось інший (спільна гілка: `! [rejected] ... (fetch first)`, `exit 1`).
**Приватну task-гілку, крім тебе, ніхто не просуває — тому push із як завгодно
застарілої бази проходить з `exit 0`.** Успішний push нічого не каже про свіжість.

Свіжість бази встановлюється явно — перевіркою `merge-base --is-ancestor` перед
переходом у `REVIEW` і ще раз у G7 — і записується в handoff (`BASE_SHA`).
Різні task-гілки не конфліктують **при push** — це незалежні ref (перевірено); при
rebase чи merge вони конфліктують, як будь-які гілки, що торкнулися тих самих рядків.

І навіть свіжа база ловить лише **текстовий** конфлікт. Семантичний (твій код досі
компілюється, але змінилася поведінка модуля, від якого він залежить) git не бачить.
Звідси ворота G5.

## 6. Ворота

Ворота проходяться по порядку. На повному шляху G0, G1, G2, G3, G4, G6, G7 і G9
**не пропускаються ніколи**. Пропустити можна лише два: G5 — якщо одиниця не має
артефакту, що виконується (`FRESHNESS=незастосовно`), і G8 — якщо розгортання не
передбачене (`DEPLOY=NOT_APPLICABLE`); обидва — з причиною в handoff:
`SKIPPED=<ворота>: <причина>`. Будь-який інший «пропуск» — умова СТОП (розділ 9),
а не поле в handoff.

### 6.0. Скорочений шлях (аксіома A6 в дії)

Повний цикл G0–G9 — для одиниць, що змінюють поведінку. Зміна йде скороченим шляхом,
якщо виконано **все** одночасно:

```text
[ ] ≤ 2 файли, жоден не в protected_paths і не в critical_paths binding
[ ] не змінює спостережуваної поведінки: документація, коментар, typo,
    форматування, механічна правка без семантики
[ ] не торкається секретів, deployment, CI і самих тестів
[ ] не торкається секції критеріїв ЗАЯВЛЕНОЇ одиниці (перевір origin/task/* у G0): навіть
    typo там змінює текст, який G7 порівнює з копією в handoff → чужа одиниця BLOCKED
```

Скорочений шлях:

```text
G0 (sync) → G1 (прочитати, що правиш) → детермінована валідація
(лінтер / парсер / збірка) → один коміт із причиною в першому рядку:
"small-change: <що і чому>" → push
```

Без claim'у, без review-артефакта, без handoff. Куди комітити — визначає
`branches.direct_small_changes` у binding:

```text
true   → прямо в гілку інтеграції, будь-якою роллю. Це ЄДИНИЙ виняток із таблиці 6.10.
         На L1 із захистом гілки сервер такий push відхилить — тоді значення має бути false.

false  → у гілку small/<YYYYMMDDTHHMMSSZ>-<slug>, напр. small/$(date -u +%Y%m%dT%H%M%SZ)-fix-typo
         (без <ID>, бо claim'у немає; без ":" — він заборонений у refname), push, і master
         інтегрує її за G7-lite: перевіряє ВСІ чотири критерії 6.0 по diff'у, `git diff --check`
         і детерміновану валідацію, ребейзить на поточну гілку інтеграції (друга
         small/* від старої бази fast-forward не зіллється) — і зливає fast-forward.
         Master знаходить такі гілки у G0 (`origin/small/*`) і після злиття ВИДАЛЯЄ:
         `git push origin --delete small/<name>` — інакше «черга» ніколи не порожніє
         (повторний G7-lite — no-op, але робота даремна). Worker після push нічого
         більше не робить. Review-артефакт і handoff
         не потрібні. Порушення критеріїв 6.0 → гілка повертається на повний шлях.
```

Хоч одна умова не виконана — повний шлях. **Сумнів = повний шлях.** Дві «малі»
зміни в одних і тих самих файлах поспіль — це вже одна одиниця роботи, що маскується.

### G0 — SYNC

```bash
git fetch origin --prune '+refs/heads/*:refs/remotes/origin/*'
git status --short --branch
git log origin/main --oneline -15
MAIN=$(git rev-parse --git-common-dir)/..                        # основний клон, НЕ worktree (розділ 0)
git -C "$MAIN" switch -q main && git -C "$MAIN" merge -q --ff-only origin/main \
  && [ "$(git -C "$MAIN" rev-parse HEAD)" = "$(git rev-parse origin/main)" ] \
  || { echo "main ≠ origin/main — СТОП"; exit 1; }     # інакше specs/ і reviews/ в основному клоні застарілі
# Робоче дерево worktree — це task-гілка; його свіжість відносно origin/main — §5.6, не G0.
git ls-remote origin 'refs/heads/task/*' 'refs/heads/small/*'   # чужі заявки і small/* — з сервера, не з локальної копії
for b in $(git for-each-ref --format='%(refname:short)' refs/remotes/origin/task/); do
  echo "== $b"; git show "$b:specs/handoffs/${b#origin/task/}.md"; done   # handoff читається З ГІЛКИ (5.3)
git for-each-ref --format='%(refname:short)' refs/remotes/origin/small/    # master: черга G7-lite (6.0)
```

Мета — не формальність: інший агент міг закрити цю саму одиницю, поки тебе не було.
Робота від застарілого знімка — гарантований конфлікт.

### G1 — UNDERSTAND

```text
[ ] прочитано опис одиниці роботи і критерії приймання
[ ] прочитано пов'язані специфікації
[ ] перевірено, що залежності справді закриті (у git, не лише в тексті беклогу)
[ ] прочитано specs/reviews/ по суміжних одиницях — які знахідки вже дисміснуто
[ ] знайдено наявну реалізацію (можливо, задача вже частково зроблена)
[ ] оцінено вплив: архітектура / безпека / дані / deployment
```

Розбіжність між метаданими і git вирішується на користь git:

```bash
git log --all --grep="Task: TASK-001"
```

Якщо беклог каже `DONE`, а коду немає — це не привід «дореалізувати мовчки».
Це неконсистентність, яку треба зафіксувати комітом і виправити явно.

При неоднозначності вимог: `BLOCKED` + питання. **Не вигадувати вимоги.**

### G2 — TEST FIRST (жорсткі ворота)

```text
Спочатку падаючий тест. Потім реалізація.
```

Порядок обов'язковий і перевіряється:

```text
1. напиши тест
2. запусти його
3. зафіксуй RED дослівно: яка команда, який вивід, чому падає
4. переконайся, що падає САМЕ З ТІЄЇ ПРИЧИНИ, яку ти виправляєш
5. тільки тепер пиши реалізацію
```

Крок 4 суттєвий. Тест, що падає з `ReferenceError` замість очікуваного
розходження значень, не доводить нічого.

Якщо спіймав себе на тому, що редагуєш реалізацію першим: **зупинись, відкоти,
напиши тест, повернись**. Це не формальність — тест, написаний після коду,
систематично перевіряє те, що код робить, а не те, що потрібно.

Для нефункціональних змін (документація, механічні правки) RED/GREEN замінюється
детермінованою валідацією: лінтер, парсер схеми, збірка, порівняння знімка.

### G3 — IMPLEMENT

```text
мінімально
в межах одиниці роботи
без «заодно» виправлень
без зміни секретів і deployment-стану
```

Сторонній дефект, помічений дорогою, стає **новою одиницею роботи**, а не частиною цієї.
Це не бюрократія: змішана зміна не може бути коректно відрев'ювана, бо рев'юер
не може відокремити навмисне від випадкового.

### G4 — VERIFY

```bash
git diff --check
<команда тестів проєкту>
```

Фіксуються **фактичні** результати: команда, кількість пройдених/впалих, вивід помилок.

Заборонені формулювання як докази:

```text
"tests should pass"
"виглядає правильно"
"я думаю, це працює"
"логіка коректна"
```

**Фальсифікація (обов'язково для нетривіальних змін).** Зелений тест доводить менше,
ніж здається — він міг би бути зеленим і без твоєї зміни. Тому:

```text
навмисно зламай реалізацію (інвертуй умову, поверни константу)
→ переконайся, що тест ЧЕРВОНІЄ
→ поверни реалізацію
```

Якщо тест лишається зеленим на зламаному коді — він нічого не перевіряє.
Це найдешевший відомий спосіб спіймати тест-пустушку, і жодна з версій v2–v5
його не вимагала.

### G5 — FRESHNESS (нові ворота)

Ворота, яких не було в жодній попередній версії, хоча саме тут стається найдорожча
категорія помилок.

```text
Перед тим як повідомити будь-який результат, здобутий із запущеної системи,
доведи, що система виконує САМЕ ТОЙ артефакт, який ти щойно змінив.
```

Чому це критично: між твоєю зміною і твоїм виміром стоять шари, кожен з яких може
підсунути стару версію — HTTP-кеш, CDN, service worker, кеш збірки, гарячий процес,
кеш модулів, дзеркало на іншому хості.

Мінімальна перевірка свіжості:

```text
1. Внеси в артефакт унікальний маркер (версія, хеш, timestamp).
2. Прочитай артефакт так, як його бачить система під тестом.
3. Перевір, що маркер збігається.
4. Тільки після цього знімай будь-які виміри.
```

Приклади технік: порівняти звичайний запит із запитом, що обходить кеш;
додати cache-busting параметр; звірити хеш розгорнутого файлу з локальним.

Правило звітності:

```text
Вимір без доведеної свіжості — не результат.
Якщо свіжість недоведена, звіт має це прямо сказати.
```

Симетричне правило: якщо ти вже повідомив число, а потім виявив, що свіжість не
трималася — **виправ публічно**: у документі, в артефакті review і в повідомленні
людині. Тихо переписати гірше, ніж помилитися.

### G6 — INDEPENDENT REVIEW

Див. розділ 8 — незалежність рев'ю потребує окремого визначення.

### G7 — INTEGRATE (тільки MASTER)

Master інтегрує лише коли одночасно:

```text
review зійшовся, артефакт review закомічено, STATE=APPROVED
тести зелені на актуальній базі
гілка ребейзнута на поточний origin/main (перевірено merge-base, не «здається»)
конфліктів немає
секрети не потрапили в diff
текст секції CRITERIA_SOURCE на origin/main (після нормалізації чекбоксів) збігається з копією в handoff
```

Перед злиттям — фінальний огляд повного diff і перевірка критеріїв:

```bash
git fetch origin --prune
git merge-base --is-ancestor origin/main HEAD || echo "STALE — rebase first"
git diff origin/main...HEAD
git status --ignored
git show origin/main:specs/foo.md \
  | awk -v h='## TASK-001' 'BEGIN{L=index(h," ")-1} {sub(/\r$/,"")} $0==h{f=1;b=0} f&&match($0,/^`+/)&&RLENGTH>=3{if(!b)b=RLENGTH;else if(RLENGTH>=b)b=0} f&&!b&&$0!=h&&match($0,/^#+ /)&&RLENGTH-1<=L{exit} f' | sed 's/\[[xX]\]/[ ]/g' > .crit-now
sed '1,/^---[[:space:]]*$/d' specs/handoffs/TASK-001.md | sed 's/\[[xX]\]/[ ]/g' > .crit-claimed   # [[:space:]]: CR у CRLF-checkout
diff -B --strip-trailing-cr .crit-claimed .crit-now; RC=$?; rm -f .crit-claimed .crit-now
[ "$RC" -eq 0 ]          # розбіжність → STATE=BLOCKED, не інтеграція
# -B обов'язково: $(...) у 5.2 зрізає кінцеві порожні рядки копії, а секція на main
#    (якщо за нею є наступна) закінчується порожнім рядком — без -B diff ≠ ЗАВЖДИ (перевірено)
# --strip-trailing-cr: клони з CRLF; [xX]…/g: усі чекбокси в рядку
```

**Ребейз анулює контекст review.** Якщо база змінилася матеріально (зачеплено ті самі
модулі, публічні інтерфейси, схему, конфігурацію) — review потрібно повторити.
Хеш AST чи API-поверхні може бути **доказом, що зменшує невизначеність**, але не є
доказом семантичної еквівалентності (це правильно зафіксовано ще у v4 §31.2 —
залишаємо формулювання без посилення). Якщо граф залежностей встановити надійно
не вдається — консервативно вважай review недійсним.

### G8 — DEPLOY + RUNTIME (привілейована операція)

```text
MERGED != DEPLOYED != HEALTHY != CORRECT
```

Жоден із цих переходів не випливає з попереднього автоматично.
Для розгортання мають бути відомі:

```text
точний source SHA
ідентичність артефакту (digest)
авторизація
цільове середовище
ціль відкату
```

Після розгортання — перевірка **живої** системи, а не лише unit-тестів,
і обов'язково через ворота G5 (інакше перевіряється стара версія).

Мінімальний набір перевірок (конкретні очікувані коди — у `PROJECT-BINDING.md`,
не тут):

```text
health endpoint
критичний користувацький шлях
межа автентифікації/авторизації
недоступність внутрішніх файлів ззовні
ідентичність версії (чи справді розгорнуто той SHA)
```

Результат розгортання записується в окреме поле handoff'у `DEPLOY`
(`NOT_APPLICABLE | NOT_DEPLOYED | DEPLOYED | PARTIAL | UNKNOWN`), а не в `STATE`.
Частковий успіх — це `PARTIAL`, невідомий — `UNKNOWN`; обидва — умова СТОП:
`STATE=BLOCKED`, `NOTE=integrated at <SHA>; deploy PARTIAL|UNKNOWN: <що саме>`.
Факт інтеграції не губиться (він у `NOTE` і в git-історії), а `BLOCKED` захищає
одиницю від RECLAIM (5.4), поки людина чи master не розберуть стан.

### G9 — RECORD

```text
[ ] чекбокси специфікації відображають фактичний стан (не бажаний)
[ ] артефакт review закомічено
[ ] specs/handoffs/<ID>.md оновлено: STATE, DEPLOY, DONE/NOT_DONE/UNCERTAIN/NEXT (розділ 10)
[ ] беклог оновлено
[ ] гілка запушена — інакше для інших агентів роботи не існує
```

**Проставляти чекбокс до того, як робота зроблена, — заборонено.**
Це не косметика: наступний агент читає чекбокси як факти і будує на них рішення.
Передчасно позначена секція спричиняє роботу від хибної передумови.

## 7. Дисципліна доказів

Це ядро v6. Координація не дає помилятися одночасно; дисципліна доказів не дає
помилятися впевнено.

### 7.1. Формат знахідки

Кожна знахідка рев'ю має містити рівно це:

```text
шлях до файлу (абсолютний або від кореня репо)
номер рядка
дослівна цитата коду, ≤15 слів
опис проблеми
конкретний сценарій відмови: які вхідні дані/стан → який неправильний результат
```

Знахідка без цієї структури **недійсна і відкидається**.
Причина прямолінійна: мовна модель здатна згенерувати переконливий опис
неіснуючого дефекту. Вимога дослівної цитати з рядка робить вигадану знахідку
такою, що не проходить механічну перевірку.

**Той, хто отримав знахідку, зобов'язаний сам відкрити вказаний рядок і звірити цитату.**
Цитата не збіглася → знахідка відкидається без обговорення.

### 7.2. Право відхилити знахідку

Знахідку можна відхилити **тільки** так:

```text
конкретна причина, чому цей шлях виконання не може статися
        +
доказ з боку викликів (grep по всіх точках виклику)
```

Недостатньо і відхиленням не є:

```text
"виглядає нормально"
"на практиці такого не буває"
"це малоймовірно"
"тут і так усе перевіряється вище"   ← без показаного "вище"
```

При сумніві — виправляй. Вартість зайвого виправлення нижча за вартість
пропущеного дефекту, який вже пройшов рев'ю (бо наступний рев'юер побачить
його як «вже розглянуте»).

### 7.3. Правило не-повторного підняття

```text
Знахідка, ідентична вже розглянутій у попередній ітерації,
не рахується у ліміт ітерацій.
```

Ідентичність визначається **строго**: той самий `file:line` **і** та сама дослівна
цитата. Будь-яка інша відповідність — це нова знахідка.

Правило потрібне у двох напрямках одразу: без нього рев'юер може крутити цикл
нескінченно, переформульовуючи те саме, а автор — оголошувати нову знахідку
«повторною», щоб її не виправляти.

### 7.4. Обмеження циклу рев'ю

```text
максимум 3 ітерації на одиницю роботи
```

Після третьої, якщо не зійшлося:

```text
STOP → створити halt-артефакт specs/reviews/<unit-id>.halt.md
     → handoff: STATE=BLOCKED, NEXT=<посилання на halt-артефакт і хто вирішує>
```

Halt-артефакт комітиться в task-гілку (одиниця не інтегрована), тож із гілки інтеграції
його не видно — читати `git show origin/task/<ID>:specs/reviews/<ID>.halt.md` (5.3).
Сам факт halt видно з handoff тієї ж гілки (`STATE=BLOCKED`, `NEXT=` вказує на файл),
який G0 читає для кожної `origin/task/*`. Він блокує переприсвоєння за 5.4.

Halt-артефакт містить:

```text
у чому суть незакритої розбіжності
що вже перевірено і з яким результатом
що лишилося невизначеним
оцінка ризику
рекомендований наступний крок і хто його має зробити
```

Код не мутують нескінченно заради формального `PASS`. Три ітерації без збіжності —
це сигнал, що проблема в постановці задачі, а не в коді.

### 7.5. Артефакт рев'ю

```text
specs/reviews/<unit-id>-iter<N>.md
```

Заголовок — машиночитний:

```yaml
---
unit: TASK-001
iter: 1
reviewer: agent-bar
base_sha: <SHA>
head_sha: <SHA>
files-reviewed:
  - foo/a.ext
  - bar/b.ext
decision: PASS | PASS_WITH_NOTES | FAIL
---
```

Далі — знахідки у форматі 7.1, ухвалені рішення і **залишкова невизначеність**.

Артефакти попередніх ітерацій **зберігаються**. Вони — колективна пам'ять проєкту:
з них наступний агент дізнається, які знахідки вже відхилено і на якій підставі,
і не піднімає їх без нових доказів.

Повідомлення в чаті артефактом рев'ю не є.

### 7.6. Звітність про результат

```text
Що перевірено — конкретно, з командами і виводом.
Що НЕ перевірено — прямо назвати.
Залишкова невизначеність — назвати, а не замовчати.
```

Негативний або непереконливий результат фіксується як негативний. Формулювання
«не вдалося підтвердити» — валідний і цінний результат; «схоже, працює» —
ні. Якщо перевірка не відбулася — так і написати, а не пропустити рядок.

## 8. Незалежність рев'ю

### 8.1. Базове правило

```text
AUTHOR != REVIEWER
```

Кількість незалежних рев'юерів для звичайних змін — `review.min_independent` у binding
(мінімум 1; субагент із чистим контекстом зараховується лише за умов 8.2).

Для критичних змін (автентифікація, авторизація, криптографія, платежі,
руйнівні операції з даними, релізна інфраструктура, доступ до production):

```text
AUTHOR != REVIEWER != DEPLOY_AUTHORIZER
```

### 8.2. Питання, на яке жодна попередня версія не відповіла

На практиці найчастіший механізм рев'ю — це коли **агент-автор сам запускає
субагента** з чистим контекстом. v4-RedTeam §7 справедливо вказала, що
`Agent completion procedure` у v4 читається як самозатвердження. v5 проголосила
`AUTHOR != REVIEWER`, але не сказала, чи вважається таким рев'ю субагент,
породжений автором. Це найуживаніший випадок, і протокол мовчав.

Відповідь v6, явна:

> **Субагент із чистим контекстом зараховується як незалежний рев'юер тоді і тільки
> тоді, коли виконано всі чотири умови:**
>
> 1. Рев'юер **не отримує** міркувань автора: ані пояснення задуму, ані
>    «на що звернути увагу», ані причин, чому автор вважає рішення правильним.
>    На вхід — diff, релевантні файли й критерії приймання. Крапка.
> 2. Рев'юер зобов'язаний **сам прочитати цитовані рядки** й перевірити свої
>    знахідки за форматом 7.1 — не покладаючись на опис автора.
> 3. Автор **не має права** відхилити знахідку інакше, ніж за правилом 7.2,
>    і фіксує підставу відхилення в артефакті.
> 4. Результат — **durable-артефакт** (7.5), закомічений разом зі зміною.
>
> **Цього НЕ достатньо для:**
> - критичних змін за переліком 8.1 — там потрібен рев'юер в окремій сесії
>   або інший агент/акаунт; скільки саме таких рев'юерів — визначає
>   `review.critical_paths_min_independent` у binding (мінімум 1);
> - фінального `approve` перед інтеграцією в захищену гілку — цей перехід
>   виконує master, і він не може бути автором зміни. Якщо єдиний master проєкту
>   і є автором — G7 виконує інший master або людина (`escalate_to_human`); їх
>   немає — умова СТОП (розділ 9), а не самоінтеграція.

Обґрунтування чесне: субагент із чистим контекстом усуває *закріплення на власному
рішенні* — головне джерело сліпоти автора. Він не усуває спільних для моделі
систематичних помилок і не є незалежною стороною у сенсі безпеки. Тому він
достатній для звичайної роботи і недостатній там, де ціна помилки висока.

### 8.3. Обсяг рев'ю

```text
коректність            конкурентність          безпека
цілісність даних       режими відмови          сумісність
спостережуваність      продуктивність          відкат
якість самих тестів
```

Активно шукати:

```text
race condition, TOCTOU, порушення ідемпотентності, часткова відмова,
підсилення ретраїв, застарілий стан, ескалація привілеїв, витік секретів,
тиха втрата даних, небезпечний fallback, відсутній timeout,
тест, який завжди зелений
```

## 9. Умови СТОП

Будь-яка з цих ситуацій означає: зупинитися і написати, що саме сталося.
Список навмисно конкретний — узагальнене «UNKNOWN ≠ SUCCESS» з v5 правильне,
але його неможливо перевірити чеклістом.

```text
[ ] невідомо, хто зараз володіє одиницею роботи
[ ] гілку змінив хтось інший, поки ти працював
[ ] беклог/специфікація суперечать git-історії
[ ] тести неможливо запустити або вони нестабільні без з'ясованої причини
[ ] невідомо, яка версія коду реально виконується в системі під тестом (G5)
[ ] секрет міг потрапити в diff або в артефакт
[ ] конфлікт має неочевидну семантику (не текстову)
[ ] специфікація суперечить реалізації, і незрозуміло, що з них правильне
[ ] стан залежності невідомий
[ ] rebase змінив базу, і незрозуміло, чи лишається review валідним
[ ] одиниця роботи виявилася більшою, ніж описано, і торкається чужих шляхів
[ ] потрібна привілейована дія, на яку немає повноважень поточної ролі
[ ] у проєкті немає жодного агента з роллю master (2.0), а робота вимагає його переходу
[ ] власний AGENT_ID не визначено (2.0)
[ ] потрібно пропустити ворота, крім G5/G8 (розділ 6)
[ ] критерії приймання змінилися після claim (текст секції CRITERIA_SOURCE ≠ копії в handoff)
[ ] G7 потрібен одиниці, автор якої — єдиний master проєкту (8.2)
[ ] DEPLOY=PARTIAL або UNKNOWN
```

Заборонено: «припустимо, що все нормально».

## 10. Handoff

Handoff — це файл `specs/handoffs/<UNIT>.md` (шлях — з binding). Його створює
claim-коміт (5.2) і оновлює окремий коміт при кожній зміні `STATE` або `DEPLOY`;
історія версій — у git. Повідомлення в чаті handoff'ом не є (A1).

Структура файлу жорстка: усі поля `KEY=value` — **до** рядка `---`; після нього — лише
копія критеріїв, яка не редагується. Поля, що з'являються при переходах (`TESTS=`,
`REVIEW=`, `NOTE=` тощо), **вставляються перед `---`**, а не дописуються в кінець файлу:
G7 читає все після `---` як критерії, і дописаний у кінець `NOTE=` робить одиницю
неінтегрованою (перевірено).

Перед завершенням сесії — незалежно від того, чи робота закінчена — файл має
відображати фактичний стан:

```text
UNIT=TASK-001
STATE=REVIEW            # TODO|CLAIMED|ACTIVE|BLOCKED|REVIEW|APPROVED|INTEGRATED|DONE|ABANDONED
DEPLOY=NOT_DEPLOYED     # NOT_APPLICABLE|NOT_DEPLOYED|DEPLOYED|PARTIAL|UNKNOWN
OWNER=agent-foo
BRANCH=task/TASK-001
BASE_SHA=<SHA>          # origin/main, на якому реально стоїть гілка (5.6), не «на момент claim»
HEAD_SHA=<SHA>
CRITERIA_SOURCE=<шлях#заголовок секції>   # звідки скопійовано критерії; сама копія — після рядка ---
CLAIMED_AT=<UTC>
TESTS=<фактичний результат: команда + підсумок>
FRESHNESS=<доведена|не доведена|незастосовно>
REVIEW=specs/reviews/TASK-001-iter1.md
SKIPPED=<ворота: причина, або порожньо>
RISK=LOW|MEDIUM|HIGH|CRITICAL
DONE=<що фактично завершено>
NOT_DONE=<що явно не завершено>
UNCERTAIN=<що лишилося невизначеним>
NEXT=<конкретна наступна дія і хто її робить>
NOTE=<вільний текст: попередній власник при RECLAIM тощо>
---
<дослівна копія секції критеріїв приймання на момент claim (5.2); НЕ редагується після claim —
 навіть коли BASE_SHA рухається при rebase: копія фіксує критерії, BASE_SHA — базу коду>
```

Переходи `STATE` (хто виконує — таблиця 6.10):

```text
TODO → CLAIMED        успішний push claim-коміту (5.2)
CLAIMED → ACTIVE      перший робочий коміт у гілці
ACTIVE → REVIEW       G4+G5 пройдені, свіжість бази перевірена (5.6), артефакт рев'ю є
REVIEW → ACTIVE       decision FAIL (або PASS_WITH_NOTES з правками); автор допрацьовує, iter < 3 (7.4)
REVIEW → APPROVED     master закриває review, що зійшовся
APPROVED → INTEGRATED G7
INTEGRATED → DONE     G8 виконано з DEPLOY ∈ {DEPLOYED, NOT_APPLICABLE} і G9 завершено;
                      записує master — після G7 handoff-файл живе в гілці інтеграції,
                      і worker у цю одиницю більше не комітить
будь-який → BLOCKED   умова СТОП (розділ 9); назад — у той самий стан або в ABANDONED
CLAIMED|ACTIVE → CLAIMED (новий OWNER)      RECLAIM (5.4); виконує master
CLAIMED|ACTIVE → ABANDONED                  явна відмова власника або рішення master; термінальний
BLOCKED → ABANDONED                         лише master — це вихід із BLOCKED (6.10); власник не може
```

`CLAIM_LOST` — не стан, а результат невдалого push у 5.2: одиниця для цього агента
лишається `TODO`.

Критерій якості handoff:

```text
Інший агент має продовжити роботу, не відновлюючи хід твоїх думок
з коду й не ставлячи питань людині.
```

Якщо сесія завершується посеред одиниці роботи:

```text
залиш git-стан чистим
закомічена лише повністю завершена і відрев'ювана робота
незавершене — або в task-гілці з явним записом стану, або не закомічене взагалі
специфікація має чесно показувати, що зроблено, а що ні
```

## 11. Антипатерни

Наведені дослівно — саме як фрази, які агент готовий вимовити. Цей формат
успадковано з v2 §43 і виявився найдієвішим у документі; v5 його втратив.

```text
«Я сказав іншому агенту, що беру це.»
    → чат не існує для іншого агента. Claim = запушений ref/гілка.

«Я відредагував беклог локально.»
    → незапушена заявка не існує.

«Тести мають проходити.»
    → це не перевірка. Запусти і покажи вивід.

«Я перевірив власний патч.»
    → це не незалежне рев'ю. Умови зарахування — розділ 8.2.

«Я master, отже тести необов'язкові.»
    → повноваження не звільняють від якості.

«main змінився, отже production оновився.»
    → MERGED != DEPLOYED != HEALTHY.

«Виміряв на живій системі, стало швидше.»
    → доведи спершу свіжість артефакту (G5), інакше вимір нічого не значить.

«Виглядає нормально, знахідку закриваю.»
    → відхилення без доказу з боку викликів заборонене (7.2).

«Заодно підправив ще кілька місць.»
    → змішана зміна не піддається коректному рев'ю. Окрема одиниця роботи.

«Позначу секцію зробленою, дороблю потім.»
    → наступний агент прочитає це як факт і побудує на ньому рішення.

«Тест зелений, значить працює.»
    → зламай реалізацію навмисно; тест зобов'язаний почервоніти (G4).

«Конфлікт вирішив, узяв свою версію.»
    → текстовий конфлікт ≠ семантичний. Зрозумій обидва наміри.

«--no-verify, бо hook заважає.»
    → hook — частина протоколу, а не перешкода. Потрібен явний дозвіл людини
      з названими воротами.

«Заявка стара, забираю собі.»
    → лише за повним переліком умов 5.4, з явним записом RECLAIM, і лише master.

«Push пройшов — отже, база свіжа, інакше git би відхилив.»
    → git відхиляє лише спільні гілки. Приватну task-гілку він пропустить із
      будь-якої бази (5.6). Свіжість доводить merge-base, а не exit 0.

«Це дрібниця, пропущу ворота.»
    → дрібниця має точні критерії (6.0). Не підходить під них — повний шлях.
```

## 12. Прив'язка до проєкту

Цей файл **не містить** нічого проєктного. Усе конкретне — в окремому файлі
`PROJECT-BINDING.md` у корені репозиторію. Це те, чого не витримали v2 і v3:
у них у нормативний текст протекли реальні домени, шляхи й очікувані HTTP-коди
конкретного проєкту, після чого документ перестав бути переносимим.

Шаблон:

```yaml
# PROJECT-BINDING.md

protocol_version: "6.0"
conformance_level: L0        # L0 | L1 | L2 | L3 — заявляй чесно

agent_id:
  source: "git config user.name"   # звідки агент бере свій AGENT_ID (2.0); людина гарантує унікальність

roles:
  master: [<AGENT_ID, ...>]        # усі інші — worker; самопризначення заборонене (2.0)

units_of_work:
  source: specs/             # де живуть одиниці роботи
  backlog: docs/backlog.md
  reviews: specs/reviews/    # артефакти рев'ю і <id>.halt.md
  handoffs: specs/handoffs/  # <id>.md — стан одиниці (розділ 10)
  id_format: "<PREFIX>-<NNN>"
  criteria_section: "## <ID>"   # заголовок секції одиниці в спеці — ТОЧНО цей рядок, без назви після ID (5.2);
                                # назву давати наступним рядком або в тілі секції

branches:
  integration: main
  task_prefix: task/
  protected: [main]
  direct_small_changes: true   # true: 6.0 комітить прямо в integration будь-якою роллю (виняток 6.10);
                               # на L1 із захищеною integration — false (гілка small/*, G7-lite)

commands:
  test: "<команда запуску тестів>"
  lint: "<команда лінтера>"
  build: "<команда збірки>"
  freshness_check: "<як довести, що система виконує свіжий артефакт>"

lease:
  ttl_hours: 24

review:
  min_independent: 1                 # субагент із чистим контекстом зараховується (8.2)
  critical_paths_min_independent: 1  # рев'юери ПОЗА сесією автора (8.2); підвищуй, якщо ціна помилки того варта
  critical_paths:
    - <шляхи, де ціна помилки висока>

protected_paths:
  - MULTI-AGENT.md
  - PROJECT-BINDING.md
  - specs/architecture/**
  - specs/security/**
  - <CI-конфігурація, deployment-скрипти>

secrets:
  never_commit:
    - <перелік шляхів>

deployment:
  targets: [<середовища>]
  authorization: <хто і як авторизує>
  smoke_checks:
    - "<перевірка> → <очікуваний результат>"
  rollback: <як саме відкочуємося>

escalate_to_human:
  - зміна моделі довіри або архітектурних інваріантів
  - руйнівні операції з даними
  - ротація або скидання облікових даних
  - послаблення політики безпеки
  - будь-що незворотне
```

Правило: якщо агент збирається зробити щось, чого немає в `PROJECT-BINDING.md`,
і воно незворотне — це `escalate_to_human`, а не рішення за замовчуванням.

## 13. Чого цей протокол не гарантує

Розділ обов'язковий. Протокол, що не називає своїх меж, породжує хибну впевненість —
рівно ту, проти якої він написаний.

```text
Не гарантує коректності міркувань агента.
Не гарантує відсутності дефектів.
Не гарантує семантичної еквівалентності після rebase.
Не гарантує, що тест перевіряє те, що заявлено (частково закриває G4/фальсифікація).
Не гарантує стійкості до зловмисного агента або скомпрометованого master.
Не гарантує, що захищену гілку не змінить адміністратор сервера в обхід захисту (L1).
Не гарантує нічого на L0, крім видимості порушень у git-історії постфактум.
```

І головне:

```text
ЗАДОКУМЕНТОВАНА ПОЛІТИКА  ≠  ПРИМУСОВО ЗАБЕЗПЕЧЕНА ПОЛІТИКА

Реальний контроль = політика + машинний примус + довговічні докази.
На L0 машинного примусу немає. Є дисципліна і аудитований слід.
Це треба називати вголос, а не приховувати за схемою даних.
```

## 16. Підсумкове правило

```text
Не роби дії, результат якої наступний агент не зможе відновити
з одного лише стану репозиторію.
```

І, як межа для будь-якого звіту:

```text
Кажи, що перевірено.
Кажи, що не перевірено.
Кажи, що лишилося невідомим.
Не видавай невідоме за успішне.
```

Master отримує більше повноважень, але не менше перевірки.
Worker отримує менше повноважень, але ті самі стандарти якості.
