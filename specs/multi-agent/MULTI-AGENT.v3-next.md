## 1. Слабкі місця та вектори атак/збоїв у протоколі v3

### 1.1. Координаційний шар (Git Refs & Claim Races)

1. **Гонка атомарного пушу** **`refs/coordination/claims/`** **(Push-race Latency):**



   - *Проблема:* Git підтримує атомарне оновлення рефів, але на рівні протоколу `git push origin refs/coordination/claims/TASK-1` під час конкурентного пушу від двох агентів один отримує відмову (Non-fast-forward / rejected).



   - *Уразливість:* Якщо Агент-А і Агент-Б одночасно надсилають реф, Агент-Б отримує відмову. Але якщо мережевий запит Агента-А пройшов на сервер, а відповідь "OK" від сервера перервалася через мережевий збій, Агент-А вважатиме, що він **втратив** claim (`CLAIM_LOST`), тоді як сервер записав його як власника. Система входить у стан **Unowned Lock (Заблукане володіння)**.



2. **Витек і захаращення рефів (Ref Namespace Leak):**



   - *Проблема:* Використання окремих `refs/coordination/claims/<TASK_ID>` призводить до швидкого розростання дерева refs у Git-репозиторії (тисячі об'єктів при активній розробці).



   - *Наслідок:* Уповільнення команд `git fetch` та `git ls-remote` для всіх агентів. Потрібен чіткий протокол **Garbage Collection (GC) для координаційних посилань** після завершення таски (`DONE`/`CANCELLED`).




### 1.2. Механіка лізингу, Heartbeat та Split-Brain

1. **Атака підсилення Heartbeat (Heartbeat Denial of Reclaim):**



   - *Проблема:* Зациклений або заблокований ("збожеволілий") Агент може продовжувати надсилати суто механічний Heartbeat (через фоновий таймер/скрипт `agentctl heartbeat`), але фактично не виконувати код таску.



   - *Наслідок:* Таск залишається навічно заблокованим у стані `ACTIVE`, і Reclaim-протокол його не забирає, оскільки `LastHeartbeatUTC` оновлюється.



2. **Split-Brain під час Reclaim (Livelock / Race on Reclaim):**



   - *Проблема:* Агент-1 вважає, що його лізинг ще дійсний (наприклад, через розсинхронізацію системного годинника локальної машини та сервера Git). Агент-2 робить `RECLAIM` і силою переписує реф claims.



   - *Наслідок:* Обидва агенти паралельно працюють над однією таскою у своїх ізольованих worktree і роблять комміти. При спробі здати в `REVIEW` виникає деструктивний конфлікт результатів (Double Work & Conflicting Reviews).




### 1.3. Merge Queue, Review та Protected Main

1. **Інвалідація рев'ю при зміні бази (Stale Review Invalidation Gap):**



   - *Проблема:* Таск пройшов Independent Review на `BaseSHA = A`. Поки він чекав у Merge Queue, в `main` злилися інші таски (база стала `B`). Агент зробив `git rebase origin/main`.



   - *Уразливість:* Розділ 33 каже: *"Якщо rebase змінює семантичну поведінку, повторіть рев'ю"*. Проте **як агент (або скрипт) визначає, що семантична поведінка змінилася?** Якщо дифф коду залишився чистим, але змінилася логіка в залежному модулі (наприклад, додано новий параметр у суміжний сервіс), старе рев'ю стає недійсним, але формально проходить як `APPROVED`.



2. **Пантомна черга мерджу (Merge Queue Deadlock):**



   - *Проблема:* Якщо в Merge Queue знаходиться 5 PR від різних агентів, і PR №2 падає на спекулятивному CI-збірці, уся черга вище PR №2 має бути відкинута та перерахована (re-tested against new base). В v3 відсутній алгоритм реагування Слейвів на випадання з Merge Queue.




### 1.4. Ізоляція та безпека

1. **Забруднення shared-ресурсів поза Git (Shared State Pollution):**



   - *Проблема:* Ізоляція через Worktree та окремі ENV змінні (наприклад, `PORT=18001`, `DB_SCHEMA=agent_142`) працює лише тоді, коли код **ідеально** поважає ці змінні.



   - *Наслідок:* Якщо Слейв виконує тесовий скрипт, у якому жорстко зашито шлях до `/tmp/cache` або до порту `6379` (Redis), або створює глобальні фонові процеси/демони, він отруює середовище для інших паралельних worktree на тій же машині.



2. **Ескалація привілеїв через сублогіку (Subagent Escalation):**



   - *Проблема:* Роль `Slave` обмежена протоколом, але Слейв контролює код, який запускається локально під час `TEST` та `VERIFY`.



   - *Уразливість:* Збожеволілий або зациклений Слейв може згенерувати тест, який виконує `git push origin main --force` або модифікує `.git/config`, обходячи обмеження `agentctl`.




# Пропозиції покращень для MULTI-AGENT.v4.md

Щоб закрити всі виявлені критичні діри розподіленої системи, пропоную внести наступні суттєві доповнення.

## Покращення 1: Fence Tokens (Запобігання Split-Brain та Livelock)

Щоб унеможливити ситуацію, коли "витіснений" Агент за інерцією перезаписує результати, вводиться монотонно зростаючий **Fence Token (Monotonic Incarnation Sequence)**.

### Формат координаційного рефу:

Plaintext

```
refs/coordination/claims/<TASK_ID> -> commit {
  task_id: "API-142",
  fence_token: 4,                  # Збільшується при кожному RECLAIM
  agent_id: "claude-3770",
  lease_until: "2026-09-05T12:00:00Z"
}

```

### Правило Fence Token:

- Будь-яка пуш-операція гілки `task/<TASK_ID>`, створення артефакту рев'ю або оновлення статусу **ПОВИННІ містити поточний** **`fence_token`**.



- Якщо Агент-1 був витіснений через `RECLAIM`, Агент-2 отримує `fence_token = 5`.



- Коли Агент-1 пробує запушити результати або оновити стан, сервер/CI відхиляє його запит, бо `4 < 5`. Агент-1 миттєво зупиняється.




## Покращення 2: Active Heartbeat & Task Progress Verification

Щоб уникнути атаки "порожнього Heartbeat", оновлення лізингу прив'язується до наявності **підтвердженого прогресу коду або тестів**.

YAML

```
# .backlog/leases/API-142.yml
task_id: API-142
agent_id: claude-3770
fence_token: 4
heartbeat_utc: "2026-09-04T22:00:00Z"
head_sha: "a1b2c3d4"            # MUST change between long heartbeats!
execution_state_hash: "e5f6g7h8" # Hash of local test execution log

```

**Правило:** Якщо під час надсилання Heartbeat параметр `head_sha` та `execution_state_hash` не змінилися порівняно з N попередніми періодами (наприклад, 2 heartbeat-інтервали поспіль), лізинг **не продовжується**, а таск автоматично помічається як `STUCK` та підлягає скиданню в `TODO`.

## Покращення 3: Формальний GC (Garbage Collection) для Координаційних Рефів

Додати чіткий цикл очищення Git-простору назв.

Plaintext

```
       TASK DONE / CANCELLED
                 │
                 ▼
Archive Manifest to .backlog/archive/
                 │
                 ▼
Delete ref: refs/coordination/claims/<TASK_ID>
                 │
                 ▼
Delete branch: task/<TASK_ID>

```

Це зберігає Git-дерево легким, запобігаючи деградації продуктивності `git fetch` при масштабуванні до сотень тасків.

## Покращення 4: Автоматична Інвалідація Рев'ю (Semantic Base Validation)

Замість суб'єктивної оцінки Агентом, чи змінив `git rebase` семантику, вводиться суворе алгоритмічне правило **Base Invalidation Check**:

Plaintext

```
При виконанні git rebase origin/main:

1. Розрахувати API/AST Surface Hash до rebase (HashA)
2. Розрахувати API/AST Surface Hash після rebase (HashB)
3. Розрахувати Diff залежних модулів у target main

ЯКЩО (HashA != HashB OR змінилися файли з exclusive_paths/specs):
   Стан REVIEW/APPROVED скасовується -> Скидання в ACTIVE
   Потрібне ПОВТОРНЕ Independent Review!

```

## Покращення 5: Сандбоксинг та обмеження права виконання (Agent Sandbox Boundary)

Для захисту локального середовища та репозиторію від збожеволілих/помилкових дій Агентів:

1. **Git Hook Enforcement (****`.git/hooks/pre-push`****):**

   Перевіряє, що пуш іде **виключно** в дозволену гілку `task/<TASK_ID>` і **ніколи** в `main` або сторонні рефи claims.



2. **Environment Jail (Контейнеризація):**

   Запуск `TEST` та `IMPLEMENT` рекомендовано виконувати всередині ephemeral Docker/Podman контейнерів або з обмеженими правами користувача ОС (Unprivileged user), що унеможливлює вихід за межі директорії worktree та доступ до мережевих портів інших агентів.

## 1. Архітектурна Доктрина
Цей документ визначає протокол взаємодії розподіленої мультиагентної AI-системи, що використовує Git як джерело істини (Single Source of Truth, SSOT) та транспортний рівень для координації (Distributed Lock Manager).

### 1.1. Базові аксіоми
1. **Код і Стан — невіддільні.** Координаційний стан системи зберігається безпосередньо в репозиторії Git, у просторі імен `refs/coordination/*`.
2. **Агенти ненадійні (Byzantine/Fail-Stop).** Будь-який агент може зависнути, втратити зв'язок з мережею, зациклитися або надати хибний звіт. Протокол має бути стійким до цього.
3. **MERGED != DEPLOYED != HEALTHY.** Протокол жорстко розмежовує стан злиття коду, його розгортання та фактичну працездатність.

## 2. Координаційний Шар (Distributed Locking & Claims)

Відмова від файлових блокувань на користь атомарних посилань Git (Git Refs).

### 2.1. Структура Координаційного Рефу (Claim Ref)
Кожне завдання відстежується через окремий об'єкт Git за адресою `refs/coordination/claims/<TASK_ID>`. Вміст рефу вказує на blob/commit із JSON-маніфестом лізингу:

```json
{
  "task_id": "CORE-104",
  "agent_id": "slave-node-a-4f92",
  "fence_token": 5,
  "lease_until_utc": "2026-09-05T10:14:00Z",
  "status": "ACTIVE",
  "proof_of_progress": {
    "head_sha": "a1b2c3d4",
    "execution_state_hash": "e5f6g7h8",
    "last_heartbeat_utc": "2026-09-04T22:14:00Z"
  }
}

````

### 2.2. Механіка Fence Tokens (Захист від Split-Brain)

Щоб уникнути ситуації, коли два агенти працюють над одним завданням (через розсинхронізацію часу або мережевий збій), впроваджено `fence_token` (монотонно зростаючий лічильник епохи).

- При зміні власника завдання (операція `RECLAIM`), новий агент **зобов'язаний** прочитати попередній стан, інкрементувати `fence_token` (N+1) і записати новий маніфест за допомогою атомарного Compare-And-Swap (через `git update-ref`).



- **Правило Бар'єру:** Сервер/Merge Queue відхиляє будь-які PR, комміти або статуси від Агента, якщо його локальний `fence_token` менший за серверний `fence_token` у координаційному рефі.




## 3. Liveness Protocol: Лізинг та Proof-of-Progress Heartbeats

У v3 агент міг нескінченно оновлювати лізинг без фактичної роботи. У v4 впроваджено **Proof-of-Progress (Доказ прогресу)**.

### 3.1. Глибинний Heartbeat

Агент зобов'язаний надсилати heartbeat кожні 15 хвилин. Щоб heartbeat був прийнятий координатором (або атомарним пушем), він повинен відповідати правилам:

1. `head_sha` поточної робочої гілки `task/<TASK_ID>` повинна змінитися хоча б раз за останні 2 інтервали (30 хвилин). Це означає створення коммітів.



2. АБО `execution_state_hash` (хеш-сума логів тестів/дебагу) повинна змінитися, підтверджуючи, що агент виконує тестування/скрипти.




### 3.2. Автоматична експропріація (Reclaim/Eviction)

Якщо умова Proof-of-Progress не виконується, або `last_heartbeat_utc` застарів:

1. Будь-який інший вільний Агент може виконати `RECLAIM`.



2. Завдання повертається в пул (status `TODO`), `fence_token` збільшується.



3. Робоча директорія старого агента (Worktree) підлягає ізоляції та видаленню примусово.




## 4. Ізоляція та Життєвий Цикл Робочих Просторів (Worktree & Jail)

### 4.1. Контейнеризація та Git Worktrees

Агенти ніколи не працюють у спільній директорії. Для кожного завдання:

1. Виконується `git worktree add ../worktrees/<TASK_ID> -b task/<TASK_ID>`.



2. Виконання тестів, збірок або скриптів впровадження відбувається **виключно у Sandbox-середовищі** (ephemeral Docker container, або обмежений unprivileged OS-user із мережевими квотами).



3. Це унеможливлює "забруднення" спільних ресурсів машини-хоста (Shared State Pollution).




### 4.2. Garbage Collection (GC) простору імен Git

Для уникнення деградації продуктивності репозиторію через тисячі старих `refs/coordination/claims/*`:

- При переході завдання в стан `DONE` (завершено) або `DEAD` (скасовано назавжди), маніфест архівується у фізичний файл `/.backlog/archive/<TASK_ID>.json`.



- Агент-Координатор (Master) виконує видалення: `git update-ref -d refs/coordination/claims/<TASK_ID>` та `git push origin --delete refs/coordination/claims/<TASK_ID>`.




## 5. Протокол Інтеграції: Merge Queue та Детермінована Інвалідація Рев'ю

Оптимістичне злиття та рев'ю вразливі до зміни базової гілки (Stale Review/Integration Races). v4 формалізує цей процес.

### 5.1. Merge Queue (Спекулятивне злиття)

1. Коли таск переходить в `REVIEW_PASSED`, він стає в чергу `Merge Queue`.



2. Координатор (CI або Master-Agent) бере гілки з черги та спекулятивно виконує `git merge` у тимчасову гілку `refs/coordination/merge_queue/target`.



3. Якщо на будь-якому етапі (наприклад, PR №2 з 5) тести падають, **вся черга після нього скидається**. Усі таски (PR 3, 4, 5) позначаються як `REBASE_REQUIRED`.




### 5.2. Алгоритмічна Інвалідація Рев'ю (AST / API Surface validation)

Якщо гілка `task/<TASK_ID>` вимагає `git rebase origin/main` через оновлення `main`, попереднє схвалення (`REVIEW_PASSED`) не може залишатися автоматично валідним.

Впроваджується **Semantic Base Validation**:

- Під час rebase розраховується дельта AST (Abstract Syntax Tree) або API-поверхонь модифікованих файлів до і після злиття з новою базою.



- Якщо файли, що залежать від змінених у `main` модулів, або їхні експортовані інтерфейси змінилися — статус примусово знижується до `ACTIVE/REVIEW_REQUIRED`. Незалежний рев'ювер повинен перевірити логіку заново.




## 6. Матриця Станів (State Machine) та Переходи

| **Поточний Стан** | **Дозволені Дії (Тригери)**   | **Наступний Стан** | **Вимоги (Guardrails)**                               |
| ----------------- | ----------------------------- | ------------------ | ----------------------------------------------------- |
| `TODO`            | `CLAIM` (Агент бере в роботу) | `ACTIVE`           | Створення `refs/.../claims/ID` з новим `fence_token`. |
| `ACTIVE`          | `HEARTBEAT` (Timer)           | `ACTIVE`           | `head_sha` OR `execution_hash` MUST change.           |
| `ACTIVE`          | `RECLAIM` (Timeout/Stuck)     | `TODO`             | Інкремент `fence_token`, відкликання лізингу.         |
| `ACTIVE`          | `SUBMIT` (Локальні тести ОК)  | `REVIEW`           | Наявність артефактів тестів, чистий Git status.       |
| `REVIEW`          | `APPROVE` (Інший Агент)       | `MERGE_Q`          | Перевірка `fence_token` автора завдання.              |

## 7. Вектори Атак та Їх Мітигація в v4 (Security & Edge Cases)

1. **Гонка Атомарного Пушу (Push-Race Latency):**



   - *Сценарій:* Два агенти одночасно беруть `TODO`.



   - *Мітигація:* Використання `--force-with-lease` або Compare-And-Swap. Лише один пуш координаційного рефу буде успішним на сервері Git. Невдаха автоматично відкочується.



2. **Атака "Порожній Heartbeat" (Livelock):**



   - *Сценарій:* Скрипт агента завис, але таймер сервісу продовжує слати heartbeats, блокуючи завдання.



   - *Мітигація:* Сервер/Протокол відхилить heartbeat, оскільки `proof_of_progress` (хеші коду/логів) не змінилися. Таск стане доступним для `RECLAIM`.



3. **Ескалація Привілеїв (Privilege Escalation):**



   - *Сценарій:* Сгенерований код намагається виконати `git push origin main --force`.



   - *Мітигація:* Git Hooks (`pre-push`) на рівні інфраструктури + запуск код-генерації у Sandboxed Worktree із забороною модифікації глобального `.git/config`.
