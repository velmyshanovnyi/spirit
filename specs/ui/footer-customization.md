# Спека: Налаштування підвалу — видимість/порядок пунктів + кастомні HTML-блоки

Запит користувача (2026-07-31): окремий розділ у Налаштуваннях, що
дозволяє (а) вмикати/вимикати кожен пункт підвалу (LICENSE/GitHub/docs/
build/розширений режим) і міняти їх порядок, (б) додавати довільні
"порожні" HTML-блоки (код/лінки/картинки/що завгодно), які
переставляються в ТІЙ САМІЙ послідовності разом з фіксованими пунктами.

## Архітектурне рішення: переюзати `order`/`boolean`-патерн design-settings, новий модуль для динамічного списку

Видимість+порядок ФІКСОВАНИХ пунктів підвалу — точна копія вже наявного
патерну `headerControlsOrder` (`designSettingsRegistry.js`, `type: "order"`)
і `visibility`-категорії (`type: "boolean"`) — жодної нової концепції.
Але кастомні блоки НЕ вписуються в цей патерн: `type: "order"`
розрахований на ФІКСОВАНИЙ, наперед відомий список `items` -- кастомні
блоки користувач додає/видаляє довільно в рантаймі, тож потрібна власна,
динамічна структура. Тому: новий модуль `client/js/footerRegistry.js`,
окремий від `designSettingsRegistry.js` (не силувати чужу абстракцію),
але той самий дизайн-принцип (localStorage, `applyX(doc)`-функція, що
викликається при кожній зміні й на старті).

### Модель даних

Три окремі ключі `localStorage`:
- `spirit.footer.itemsVisible` — `{ [fixedItemKey]: boolean }`, дефолт
  "видимий", якщо ключа немає.
- `spirit.footer.customBlocks` — `[{ id, html }]`, кастомні блоки,
  порожній масив за замовчуванням.
- `spirit.footer.order` — **єдиний спільний** список записів, де кожен
  запис — або ключ фіксованого пункту (`"license"`, `"github"`, `"docs"`,
  `"version"`, `"advancedToggle"`), або `"custom:<id>"` для кастомного
  блоку. Це і є "кастомне переміщення послідовності як і інші пункти" --
  фіксовані й кастомні пункти живуть в ОДНОМУ списку, переставляються
  тими самими ▲/▼-кнопками.

**Узгодження (reconciliation) при читанні порядку**: якщо збереженого
`order` немає -- дефолт: фіксовані пункти в порядку реєстру + наявні
кастомні блоки в кінці. Якщо є, але не містить якогось запису (новий
щойно доданий кастомний блок, чи майбутній новий фіксований пункт) --
цей запис додається в кінець. Якщо містить запис, чий кастомний блок
видалений -- запис відкидається. Це той самий "forward-compatible"
принцип, що вже неявно є в `designSettingsRegistry.js`'s `getDesignSetting`
для `type: "order"` (перевірка `parsed.length !== validKeys.length`),
але тут явний і активний (не просто "скинь до дефолту при розбіжності"),
бо довжина списку тут ЗМІНЮЄТЬСЯ користувачем регулярно (додавання/
видалення блоків), а не лише зрідка (нова версія коду).

### Рендер: CSS `order`, не пересортування DOM

Той самий прийом, що й `headerControlsOrder` (`applyDesignSettings`):
кожному елементу підвалу (фіксованому чи кастомному) виставляється
inline `style.order = <позиція в комбінованому списку>` -- `.app-footer`
вже `display:flex`, тож видимий порядок йде за CSS `order`, а не за
порядком у DOM. Фіксовані пункти лишаються статичним HTML в
`index.html` (як зараз, з `id`/`selector`, що вже є); кастомні блоки --
нові `<div class="footer-custom-block" data-block-id="...">` з
`innerHTML = block.html`, створювані/оновлювані/видалювані з DOM у
`applyFooterSettings(doc)` при кожній зміні, дописуються всередину
`#app-footer`.

### Безпека кастомного HTML: свідомо прийнятний ризик, той самий рівень довіри, що й design-налаштування

`innerHTML` з довільним, введеним самим користувачем текстом --
технічно "self-XSS"-поверхня, але:
- Значення живе ВИКЛЮЧНО в `localStorage` цього браузера -- ніколи не
  синхронізується, не надсилається на сигнальний вузол, не ділиться з
  іншими користувачами (той самий `zero-database`-інваріант проєкту:
  жодних персональних налаштувань поза власним пристроєм). Немає
  механізму, яким ЧУЖИЙ введений HTML міг би опинитися в ЦЬОМУ підвалі.
  Порівняно з CSP: `style-src 'unsafe-inline'` вже дозволений (design
  settings), і `object-src 'none'`/відсутність `'unsafe-eval'` в
  `script-src` лишаються чинними -- кастомний `<script>`-тег у
  вставленому HTML не виконається (браузери не виконують `<script>`,
  вставлений через `innerHTML`), кастомний `<img onerror=...>` міг би
  спрацювати -- та й спрацював би ЛИШЕ в браузері самого користувача,
  який сам це вставив (той самий клас ризику, що редагування власного
  CSS чи вставка HTML у DevTools-консоль -- не нова межа довіри).
- Це узгоджується з прямим запитом користувача ("кастомного встановлення
  ХТМЛ коду чи лінків чи картинок") -- обмежувати до "лише посилань" чи
  "лише plain text" суперечило б явному запиту на довільний HTML.

## Нова секція в Налаштуваннях

Не всередині наявного `#design-settings-list` (генератор там розрахований
на реєстр `DESIGN_SETTINGS` з фіксованими типами `color`/`length`/`text`/
`boolean`/`choice`/`order` -- кастомні блоки з textarea+додати/видалити не
вписуються в цей рендер без спотворення абстракції). Натомість: нова
картка на екрані `server` (там, де вже `#settings-registry-list`/
`#design-settings-list`) -- **"Підвал сайту"** (`footer-settings-list`),
власний, вручну написаний рендер (як і `renderSettingsRegistry`/
`renderDesignSettings`, той самий файл `settingsPanelUI.js`):
1. Список фіксованих пунктів: чекбокс видимості + ▲/▼ (той самий
   `order-list-item`-вигляд, що вже є для `headerControlsOrder`).
2. Список кастомних блоків: textarea з HTML-вмістом (зберігається на
   `change`/`blur`, не на кожен keystroke), кнопка "Видалити", ▲/▼.
3. Кнопка "Додати HTML-блок" -- створює порожній блок і додає його в
   кінець комбінованого порядку.
4. "Скинути" -- лише видимість+порядок (той самий принцип, що
   `resetDesignSetting`); кнопка "Скинути" НЕ видаляє вміст кастомних
   блоків (це руйнівна дія, потребує окремої явної кнопки "Видалити" на
   кожному блоці, не змішується зі "скинути презентацію").

**Рішення користувача (2026-07-31): видалення кастомного блоку --
через `window.confirm()`** (нативний браузерний діалог, без нового
UI-компонента; перший `confirm()` у проєкті -- досі не використовувався
ніде). Скасування діалогу -- блок лишається без змін.

## Що НЕ входить у цей MVP

- Санітизація/обмеження кастомного HTML (навмисно, обґрунтовано вище).
- Видимість-тумблер для кастомних блоків окремо від видалення (видалення
  -- єдиний спосіб прибрати кастомний блок; додавання -- єдиний спосіб
  його створити).
- Прев'ю/редактор WYSIWYG для HTML-блоку -- лише raw-текст у textarea.
- Ліміт кількості чи розміру кастомних блоків -- не обмежено (той самий
  рівень довіри, що й інші design-налаштування, що теж не мають лімітів).
