# Спека: Спрощений старт — лише ефемерний чат за замовчуванням (Розширений режим)

Запит користувача (2026-07-31): за замовчуванням у видимому інтерфейсі
лишається ЛИШЕ ефемерний чат (`specs/ui/ephemeral-spirit-mode.md`,
`specs/ui/chat-first-redesign.md` H5/H6). Увесь інший функціонал
(акаунти, профілі, прив'язка пристроїв, групи, імпорт, доведення
особи, соціальне відновлення, адмін-панель вузла, розширені й
design-налаштування, відеодзвінок) лишається в коді без змін, але
**перманентно прихований**, доки не розблокований явно. Розблокування
— варіант B із запропонованих п'яти (`specs/reviews/spirit-evaluation-triage.md`
не стосується; рішення записане прямо в чаті 2026-07-31): клієнтський
прапорець у `localStorage`, що вмикається паролем НА КОНКРЕТНОМУ
пристрої/браузері -- не глобально для всіх відвідувачів вузла.
Явно узгоджений шлях подальшого розвитку: перехід на гранулярні
feature-флаги (варіант E) пізніше, коли треба буде вмикати підсистеми
вибірково, а не всі одразу.

## Архітектурне рішення: пароль перевіряється БЕЗ нового серверного коду

Проєкт вже має `admin_login` server-дію (`specs/ui/server-admin-panel.md`,
Секція S1) і клієнт до неї (`client/js/adminAuth.js`'s `adminLogin(baseUrl,
password)`) -- POST на сигнальний вузол, повертає короткоживучий токен
при успіху, кидає `AdminAuthError` при неправильному паролі. Розширений
режим переюзує ЦЮ САМУ дію ЛИШЕ для перевірки пароля (успішний виклик
= пароль правильний), **токен, що повертається, ігнорується й
відкидається** -- ефект розблокування чисто локальний
(`localStorage.spirit.advancedModeUnlocked = "1"`), нуль нового
серверного коду, нуль нових PHP-тестів. Той самий `#server-url`
(поле, що вже існує в UI), використовується як `baseUrl` для виклику --
якщо поле порожнє чи вказує на вузол без сконфігурованого admin-пароля,
виклик природно провалюється з тим самим `AdminAuthError`.

**Наслідок цього рішення**: розблокування вимагає знання ТОГО САМОГО
пароля, що вже захищає read-only адмін-панель вузла (`ADMIN_PASSWORD`
у `server/config.secrets.php`, не в git) -- жодного нового секрету не
заводиться. Це узгоджується з тим, що пароль і так задуманий як
"спільний секрет для операторів/тестувальників вузла", не як тверда
межа безпеки (сам факт, що клієнт МІГ БИ технічно просто виставити
`localStorage` напряму через консоль браузера -- це свідомо прийнятний
компроміс: мета фічі не "заборонити технічно підкованому відвідувачу
побачити код", а "показати звичайному відвідувачу чистий, простий
продукт за замовчуванням").

## Точка входу для розблокування: підвал (footer), а не навігація

Проблема курки-і-яйця: якщо ВСЯ навігація (`#settings-menu`, гвинтик
налаштувань) ховається разом з рештою "розширеного" функціоналу,
нізвідки викликати форму розблокування. Рішення: нове посилання
"Розширений режим" / "Заблокувати розширений режим" **у вже наявному
`#app-footer`** (Секція footer-1, щойно доданому) -- підвал ЗАВЖДИ
видимий незалежно від режиму, поруч з LICENSE/GitHub/docs. Клік відкриває
невелику модалку з полем пароля (заблокований стан) або одразу перемикає
назад у простий режим без пароля (розблокований стан -- "замкнути" не
потребує підтвердження, це не про безпеку, а про UI-чистоту).

## Що саме ховається за замовчуванням (заблокований стан)

Список DOM-елементів/секцій, підтверджений читанням `client/index.html`
і живою інспекцією UI в цій сесії:

- **Шапка**: `#guest-quick-actions` (Створити/Увійти), `#header-call-controls`
  (дзвінок/камера/мікрофон), `.settings-wrap` (гвинтик + `#settings-menu`
  з усіма пунктами навігації -- Профіль/Кімната/Чат-як-окремий-екран/
  Історія/Сервер/Вийти). Мова (`#lang-select`) і тема (`#theme-toggle`)
  лишаються видимими -- вони НЕ належать до "закритого кейсу", це
  base UI, не пов'язаний з акаунтами/messenger-функціоналом.
- **Сайдбар** (`#app-sidebar`): увесь -- пошук, чипи-фільтри, дерево
  папок, список контактів, кнопка "Керування" (веде на групи/імпорт).
  В ефемерному режимі немає постійних контактів за визначенням.
- **Екрани-маршрути** (`data-screen`): `profile`, `server`, `room`
  (як окремий екран -- інвайт-лінк і так буде доступний з самого чату,
  RF/H6), `manage`, `history`. Лишається доступним `conversation`.
  `#settings-registry-list`/`#design-settings-list` (RF13/design
  settings) і адмін-панель вузла (S1/S2) -- усі живуть на екрані
  `server`, тож ховаються разом з ним автоматично.

  **`account` НЕ входить у список обмежених маршрутів** (архітектурне
  відкриття під час імплементації SM3): `router.js`'s `defaultRoute`
  вже дорівнює `"account"`, і `"conversation"` сам по собі
  identity-gated (`GATED_ROUTES`) -- ідентичність генерується
  АСИНХРОННО через `autoStartChat` (H5), уже ПІСЛЯ того, як роутер
  синхронно відрендерив перший екран. Якби `account` теж був
  обмеженим, редірект каскадував би: `account` (обмежений) ->
  `conversation` (redirect target) -> `conversation` (identity-gated,
  ще нема ідентичності) -> `account` (defaultRoute) -> знову
  обмежений -> нескінченний цикл. Замість цього `account` лишається
  винятком (як і для identity-гейту, той самий принцип) -- **UI-шлях
  туди все одно немає**: `#guest-quick-actions` (кнопки
  Створити/Увійти, єдиний спосіб дістатись `account` кліком) сам
  входить у прихований список вище, тож для звичайного відвідувача
  екран `account` практично недосяжний навіть без явного route-гейту.
  Пряме введення `#/account` у адресний рядок і сьогодні (без цієї
  фічі) на мить показує форму логіну/створення профілю, доки
  `autoStartChat` не перенаправить -- це вже наявна, а не нова,
  поведінка.

  Технічне рішення: `router.js` отримав ДРУГИЙ незалежний гейт
  (`restrictedRoutes`/`isRestricted`/`onRestricted`), з ОКРЕМОЮ ціллю
  редіректу (`restrictedRedirectRoute`, не той самий `defaultRoute`,
  що в identity-гейту) -- саме тому, що `conversation` (ціль для
  restricted-гейту) і `account` (ціль для identity-гейту) МАЮТЬ бути
  РІЗНИМИ, інакше немає способу коректно каскадувати через обидва
  гейти за один прохід без циклу.

**Рішення користувача (2026-07-31): відеодзвінок (`#header-call-controls`,
`#floating-video`) НЕ входить у "розширений" функціонал -- лишається
доступним завжди, в обох станах.** Обґрунтування: дзвінок -- частина
самого ефемерного P2P-сеансу (той самий співрозмовник, той самий
канал), не messenger-специфічна функція на кшталт акаунтів/груп/
device-linking.

## Розблокований стан

Побайтово те, що є в UI СЬОГОДНІ (нуль змін до наявного функціоналу) --
уся навігація/сайдбар/екрани повертаються, прапорець просто вимикає
CSS/JS-приховування зі списку вище. Персистентно в `localStorage` цього
браузера, переживає перезавантаження сторінки й закриття вкладки (той
самий рівень стійкості, що й `spirit.theme`).

## Рішення користувача (2026-07-31, усі три питання закриті)

1. Admin-токен з `adminLogin` -- **відкидається одразу**, жодного
   бонус-підвантаження `admin_get_config`. Найпростіший шлях, обрано.
2. Прямі URL-хеші на приховані екрани -- **редірект + коротке
   повідомлення** "розділ вимкнено", не мовчазний редірект.
3. Дзвінок/камера/мікрофон -- **лишається доступним завжди**, в обох
   станах (не входить у "розширений" функціонал).
